# CP-0051 · Answers to the round 6 specification questions

Answers to [pending-r6.md](pending-r6.md), decided on 2026-11-23 to finalize `CP-0051` and the `pkg/conformance/card/` recorder fixtures.

1. **CI-compatible bundle envelopes and evaluation tuple in `pkg/conformance/card/` (`ci.md:48, 139–150`, `contracts.md:18, 84`).**
   - Every `pkg/conformance/card/<case>/input.json` carries:
     - `event`: the `VerifyEvent` payload (`kind: "workflow_run"`, `repository`, `run: {id, attempt, workflow, head, repository, startedAt}`, `pulls`, `base`, plus `pr_body`, `commit_author?`, `records_push`, and the 8-key `evaluation_input` tuple `{repository, work, tested_commit, base, acceptance_digest, implemented: [{id, blessed_digest}], policy_blob, tenet_version}` from `contracts.md §1`).
     - `bundles`: an array of `{bundle, files}` entries where every `bundle` validates against `kit/schemas/bundle.json` (`{schema_version: 1, "x-repository", run: {id, attempt, workflow, job, index}, pr?, tested: {commit, kind, head, base}, checks: [{name, exit_code, outcome, duration_ms, report, report_sha256, inputs, "x-report-kind"?}]}`) and `files` maps each `check.report` path to its raw JUnit XML (or other runner format) report string whose SHA-256 matches `check.report_sha256` (except in `n05-bundle-refused-and-records-not-kept`, which also includes the refused artifact scenario).
   - **Spec edits:** `tenet/specs/tech-spec/contracts.md` §5 (`line 84`) and `tenet/specs/plan/alpha.0b.md` (`CP-0051` *Fixtures*, `line 83`).

2. **Requirement coverage attribution (`contracts.md:16, 84`, `evidence.md:54`).**
   - `requirements[].tests` on the proof card is computed by matching `itemResults([{id}], reports, {acceptance: declared.requirement})` against declarations explicitly tagged with the requirement ID (`[<prefix>-<n>]` or `tenet_<prefix>_<n>`, which `declaredTags` collects in `declared.requirement` anywhere at `head` per `evidence.md §3`). Requirement test counts are **never** inferred from an `[AB-n]` acceptance tag alone.
   - In `pkg/conformance/card/`, every case whose `expected.json` expects `C-1` to have `tests.expected > 0` (`p01`, `p03`–`p08`, `n03`–`n06`) tags its test declaration and report case with both `[C-1]` and `[AB-1]` (e.g., `test("[C-1] [AB-1] one retry after timeout", ...)` in `test/checkout.retry.test.ts`, with `<property name="tenet.case" value="C-1"/>` in the JUnit XML `<testcase>` so the case's `full_name` remains `"test/checkout.retry.test.ts › checkout › [AB-1] one retry after timeout"` and every `expected.json` and `expected.md` stays byte-identical).
   - **Spec edits:** `tenet/specs/tech-spec/contracts.md` §5 (`line 84`) and `tenet/specs/plan/alpha.0b.md` (`CP-0051` *Behavior*, `line 74`).

3. **Policy fallback on an invalid target revision (`ci.md:43, 145, 258`, `record.ts:268–282`).**
   - Per `CI §§2–3`, the recorder reads `tenet.yaml` and `tenet.lock` from the target (`base`). When loading policy or the lock at `base` fails, the recorder falls back to the previous valid policy at `base^` (`previousBase`, matching `src/verify/record.ts:268–282`) and records `"policy failed to load at head; using previous policy from base (tenet.yaml)"` in `card.degraded` (keeping that exact bound string in alpha.0 so existing tests and `n06`'s `expected.json` / `expected.md` remain byte-identical).
   - In `pkg/conformance/card/n06-policy-load-failure-fallback/input.json`, `repo.baseFiles["tenet.yaml"]` holds the broken YAML (`standard: 0.1.0-alpha.0\nlevel: [unclosed\n`) while `repo.previousBaseFiles["tenet.yaml"]` holds the valid prior policy, exercising the target-revision fallback directly.
   - **Spec edits:** `tenet/specs/tech-spec/ci.md` §3 (`line 145`) and §10 (`line 258`).

4. **Critical summary overflow past 60,000 characters (`ci.md:151, 237`).**
   - The recorder trims the check-run summary at 60,000 characters in the order of `CI §3` step 5: (1) `same-area` requirements, (2) passing items' test lists, (3) passing requirements.
   - If the remaining critical details (failing items, weakening, protected files, `Would have blocked`, `Degraded`, `Why`) still exceed 60,000 characters, the recorder writes the complete proof card to `refs/tenet/records` (`proof/<work>/<evaluation_id>/<run_id>-<attempt>.json`), truncates the check-run summary to at most 60,000 characters ending with `\n… (truncated at 60,000 characters · full proof card in refs/tenet/records)`, appends `"check summary exceeded 60,000 characters; full proof card in refs/tenet/records"` to `degraded`, and sets conclusion `"neutral"` (`"failure"` at `verify`/`assure`), never posting a passing conclusion for a truncated critical summary. (In `renderCheckSummary(model, limit)` as a pure synchronous helper without a records ref, throwing `RangeError("required proof details exceed the check summary limit")` remains valid.)
   - **Spec edits:** `tenet/specs/tech-spec/ci.md` §3 (`line 151`).

5. **Packet definition selection vs. pull-request acceptance block (`ci.md:147`).**
   - In alpha.0, quick changes use the pull-request description's `## Acceptance` block (`parseAcceptance(pr.body)`). When a pull request body or commit trailer names a packet (`Tenet-Task: CP-<id>` or a single changed `tenet/packets/CP-*/definition.md` from M1 / 0.1.0 on), the pull-request body's `## Acceptance` block takes precedence if present and non-empty; otherwise the named packet's `definition.md` `## Acceptance` block is used. In alpha.0 (`CP-0051`), reading `pr.body` alone satisfies the contract.
   - **Spec edits:** `tenet/specs/tech-spec/ci.md` §3 (`line 147`).

6. **Push bootstrap lock resolution and monthly records compaction (`ci.md:133, 169`).**
   - **Push bootstrap:** on `pull_request` and `workflow_run` (for a PR), the workflow bootstrap reads `tenet.lock` from the PR target `base.sha`. On `push` to the default branch (or `workflow_run` for a `push`, where `workflow_run` does not carry `event.before`), the bootstrap reads `tenet.lock` from the trusted default-branch checkout (`HEAD`, or `event.before` when present and reachable, falling back to `HEAD` when `before` is `0000…` or unreachable in a `fetch-depth: 1` clone); during `verify --record`, `policyFor` verifies the lock against `tested.base`.
   - **Retention and compaction:** in alpha.0, the recorder keeps every immutable run and advances `latest` forward-only (`ci.md §4`). Monthly compaction (from alpha.1, triggered on the first recorder write to a new `rules/<yyyy-mm>.jsonl` month file) prunes `proof/<work>/<evaluation_id>/<run>-<attempt>.json` files older than 30 days except the target of each `proof/<work>/latest` and any `evaluation_id` / `run` referenced by a record under `decisions/` or `works/`.
   - **Spec edits:** `tenet/specs/tech-spec/ci.md` §3 (`line 133`) and §4 (`line 169`).

7. **Shared-head check-run summary budget (`ci.md:137, 151`, `record.ts:325–336`).**
   - When $N > 1$ open pull requests share the same `head.sha`, each pull request gets its own `evaluation_id` and its own records under `refs/tenet/records` (`proof/pr-<number>/…`). On the single `Tenet` check run for `head.sha`, each pull request's card is rendered under the heading `Pull request #<number>\n`, separated by `\n`, with an equal per-card character budget of $\lfloor(60,000 - \text{overhead}) / N\rfloor$, and the check run's conclusion is the worst across the $N$ cards (`failure > neutral > success`), matching `src/verify/record.ts:325–336`.
   - **Spec edits:** `tenet/specs/tech-spec/ci.md` §3 (`line 151`) and `tenet/specs/plan/alpha.0b.md` (`CP-0051` *Behavior*, `line 72`).
