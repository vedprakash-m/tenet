Questions from building the independent conformance suite (`pkg/conformance/kernel-schemas/`):

1. **Schema filenames and primitive `$id`s under `kit/schemas/`:** `agents.md §5` line 136 fixes `kit/schemas/loop.json`, whereas TS §3 (`lines 54–70`), evidence §1 (`lines 7–18`), and `CP-0049` (`plan/alpha.1.md:9`) do not fix individual filenames under `kit/schemas/` for the six remaining primitives (`subject`, `actor`, `claim`, `evidence`, `decision`, `event`), `work`, `criteria`, `step-assignment`, and `step-result`. Should each get `<name>.json` with `$id` `https://vedprakash-m.github.io/tenet/schemas/0.1/<name>.json` (and evidence payload schemas embedded under `$defs` in `evidence.json`), and how does kernel `step-assignment.json` stay distinct from existing onboarding `assignment.json`?
2. **`migratePacket(old) -> {work, events, problems}` exact output contract:** `CP-0049` (`plan/alpha.1.md:10–12`) specifies the signature and invariants (preserve legacy `CP-NNNN` identity and observed `history`, create no inferred authority, leave originals intact), and TS §3 (`line 68`) notes `depends_on` moves to `work.changed` data. Which exact fields appear on migrated `work`, how are deterministic ULIDs generated for migrated `events[]` (so repeat runs match byte-for-byte, `line 15`), how do repeated/duplicate `history[]` entries map into `events[]`, and are `problems[]` `Finding` objects (`finding.json`) or `{code, message, path}` records?
3. **Evidence payload validation vs evaluator enforcement:** `evidence.md §1` (`lines 9–18`) defines payload fields per `kind`, and `CP-0049` (`line 13`) reserves `proof`, `simulation`, and `differential` until their methods ship. Should `evidence.json` enforce `kind`-specific required payload shapes (for instance flagging a `review` missing `located`/`invalid` mapping, and validating `proof`/`simulation`/`differential` structurally while keeping their runtime methods unadmitted), or only check common envelope fields at schema time?
4. **`loop.json` constraints derivable vs runtime `check --pack`:** In `agents.md §5` (`lines 136–195`), the worked loops omit optional `steps` limit (default `20`), use object shorthand `{if, goto, else}` in `route.on`, and define step kinds `agent|script|human_gate|set|route`. Which constraints belong in `kit/schemas/loop.json` (for example requiring all three `route.on` keys `advance`, `refuse`, `human-gate` and closed step `kind` enum) versus `tenet check --pack` static checks (`line 165`, such as `stop` first or `fix:<id>` backward target resolution)?
5. **Criteria schema (`kit/schemas/criteria.json`):** `CP-0049` (`plan/alpha.1.md:9`) names "criteria" alongside work, step assignment, result, loop, and evidence payloads, and TS §3.1/TS §6.2 reference acceptance items and pass rules. What is the exact object shape and `$id` of `criteria.json`?
