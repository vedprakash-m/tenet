# Answers — CP-0010 round 14

Rulings on the two pre-review questions for `CP-0010` (`tenet init`, `upgrade`, `remove`, `doctor`).

1. **Writes outside the repository (`onboarding.md §2`; `contracts.md §§8, 10`; `plan/alpha.0b.md` CP-0010)**
   - **Scope:** By default, `init` writes **only inside the repository** (`TN-PATH-ESCAPE` refuses any non-repo path in `.tenet/manifest.json`). The sole allowed outside-repo writes are the Windows local host MCP shim settings needed when a detected MCP host requires `cmd /c` (`claude`: `<USERPROFILE>/.claude.json`, pointer `/mcpServers/tenet`; `cursor`: `<APPDATA>/Cursor/User/mcp.json`, pointer `/mcpServers/tenet`; `vscode`: `<APPDATA>/Code/User/mcp.json`, pointer `/servers/tenet`; or paths strictly under an isolated `localProfileRoot` in test fixtures). Repository MCP files (`.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`) always stay portable (`npx -y @vedprakash-m/tenet@<locked> mcp`).
   - **Explicit consent (`--yes` is NOT enough):**
     - **Interactive:** preflight lists local entries separately as `Will edit locally (outside repository): <host>: <path><pointer>` and asks an explicit opt-in prompt `Edit local host settings outside the repository? [y/N] ` (default `No`, separate from `Continue? [Y/n]`). If declined, `init` leaves `local_keys: []` and prints the `cmd /c` entry to add manually if desired.
     - **Non-interactive (`--yes`):** `tenet init --yes` alone **does not** modify `~/.claude.json` or `%APPDATA%`! Passing `--local-hosts` (`tenet init --yes --local-hosts`) explicitly authorizes outside-repo writes on CLI (`p12` conformance fixtures injecting an isolated `localProfileRoot` retain `init --yes --json` confinement inside that disposable directory).
   - **Preflight & `--json`:** `plan.local_keys` (`[{host, path, pointer}]`) lists only authorized outside-repo edits (`[]` when declined/unflagged); human preflight displays `Will edit locally (outside repository): ...` when non-empty.
   - **Manifest & confinement:** Committed `.tenet/manifest.json` keeps only repo-relative entries (`created`, `blocks`, `keys`). Outside-repo edits are stored separately in git-ignored `.tenet/manifest.local.json` (`kit/schemas/manifest-local.json`: `{schema_version: 1, profile_roots, keys: [{host, path, pointer, previous, installed, previous_raw?}]}`), and pending steps use `kind: "local_key"` with `profile_root`. Every `local_key` path is confined strictly inside its `profile_roots[host]` (`TN-PATH-ESCAPE` on traversal or symlink escape).
   - **Removal & upgrade:** `remove` confines recorded `local_keys` against `.tenet/manifest.local.json`'s `profile_roots` (`TN-PATH-ESCAPE` on escape), restores `previous` / `previous_raw` (deleting wrapper files Tenet created empty when no sibling keys remain) if the owned key still equals `installed` (else records `kept: [{path, reason: "edited-by-you"}]`), and deletes `.tenet/manifest.local.json`. `upgrade` only updates `local_keys` already recorded in `.tenet/manifest.local.json`.

2. **Published vs unpublished, local, or prerelease package integrity in `tenet.lock` (`contracts.md §1`; `onboarding.md §2`; `plan/alpha.0b.md` CP-0010)**
   - **Version source:** Read `package` and `version` from the installed package's `package.json` (overridable by test `environment.installedVersion` / `environment.registry.package`), never falling back to `npm_package_version ?? "0.0.0"` when a packaged `package.json` exists.
   - **Published builds:** If `environment.registry.releases[version].integrity` or `TENET_INSTALL_INTEGRITY` is provided, validate and record it. Otherwise, when online (`!offline`) and `version !== "0.0.0"`, fetch `dist.integrity` from the registry (`npm view <package>@<version> dist.integrity --json`, permitted by PRD `R-080`). Validate the returned SRI matches `^sha512-[A-Za-z0-9+/]{86}==$`; record `{schema_version: 1, package, version, integrity, kit_sha256}` in `tenet.lock`.
   - **Unpublished, local, or prerelease builds (`0.0.0`, unpublished `.tgz` release candidates tested under `onboarding.md §4` step 3 and `CP-0016`, registry 404 / not published, or `--offline` with no registry override):** `init` and `upgrade` **must not fail** and **must never throw `TN-INTERNAL`**. Instead, compute a deterministic `sha512-<86 base64>==` SRI over the sorted installed package files (`package.json`, `LICENSE`, `README.md`, `dist/**`, `kit/**`, `pkg/{migrations,conformance,hosts}/**` as `<path>\0<bytes>`), write it to `tenet.lock.integrity` with `"x-integrity-source": "local"` (keeping `kit/schemas/lock.json` valid), and warn plainly (in CLI stderr / `findings` note, without blocking `init` exit `0`) that `@vedprakash-m/tenet@<version>` is not on the registry so CI workflows cannot verify it until published and re-pinned via `tenet upgrade`.
   - **Refusal code (when integrity is unusable):** If an explicit override or registry response supplies malformed/non-SHA-512 integrity (not matching `^sha512-[A-Za-z0-9+/]{86}==$`), or registry lookup fails unexpectedly for reasons other than absent/unpublished (`E404`) or offline, refuse cleanly with registered `TN-LOCK-INVALID` (`contracts.md §13` exit `1`; `messages.md §2`: `"Lock file tenet.lock is invalid: {detail}."` / `"Fix tenet.lock or run \`tenet init\` to regenerate it."`), never `TN-INTERNAL`.
