# CP-0010 · Round 5 install fixture proposals

The cases under `pkg/conformance/install/` use the contract at `18bc39f`. Exact files are present for stated byte equalities and canonical exit/finding pairs. For unresolved output, the corresponding exact fixture file is absent. The decisions below describe the first missing golden for each case and propose an answer for the Owner.

| Question | Spec and fixture evidence | Proposed answer |
|---|---|---|
| Q1 · What is the exact command result and preflight view? | Contracts §8 line 128 names top-level result fields. It leaves the `plan` item type, `wrote` type and order, `changed`/ `kept` item forms, host capability values, and how prompt choices appear open. UX Part 1 lines 34–50 illustrates a text transcript for different inputs. | Publish canonical schema and reference examples for all four commands. Use repository-relative paths, group writes by file/block/key, order group entries by UTF-16 path and then pointer, attach stable reason codes, and specify which prompts and messages appear on stderr when `--json` is used. |
| Q2 · Which exact bytes and release inputs create the first tree? | Onboarding §2 lines 75–83, Contracts §10 lines 148–158, Agents §1 lines 9–52 and CI §3 lines 87–133 give formats and templates with fill-ins. They leave versioned template identity, workflow action SHA pins, code-owner-to-owner IDs, the check name and the serialization of policy, lock, manifest and workflow output open. | Publish a release fixture bundle with pinned template bytes, action SHAs, package integrity and a versioned manifest writer. Pin LF and one final newline for generated files. Specify stable check names, owner rendering and exactly how file hashes in the lock are computed over the packaged tree. |
| Q3 · What makes runner discovery and Setup exact? | Contracts §6 lines 90–100 fixes runner and reporter commands but uses `<name>`. CI §2 lines 50–69 defines setup precedence. The default report and check names, the encoding of setup steps, and the marked byte edits are open. | Use `test` as the ordinary synthesized check key. Publish per-runner examples and deterministic selection when more than one test job or runner fits. Preserve other workflow bytes and keep only shell `run` setup commands in policy. Keep toolchain setup in the generated workflow. |
| Q4 · What exactly does empty init write? | CP-0010 line 70 and UX Part 1 line 119 require the `other` starter with `--yes`. The two prompts, default purpose, seed file substitutions, and first-finding summary for an unborn repository have no exact example. | Publish the `other` starter's pinned empty-input output. In `--yes` skip prompts and record purpose as undecided. Keep the draft unblessed and offer onboarding after setup. |
| Q5 · What byte-preserving edits are managed? | ALG-12 lines 183–194 requires restoration of the original examples and retention of changed values. Contracts §10 line 148 and Onboarding §2 line 83 leave serialization and restoration of JSON whitespace, existing managed-block baselines, and unrelated CRLF bytes open. | Keep unmanaged bytes intact. When a user entry changed, leave the entire changed value untouched. Define byte-preserving JSON insertion and inversion, or store enough prior lexical information to restore the original bytes when surrounding content matches. Define how init adopts a pre-existing marked block and which bytes are restored when it removes that adopted block. |
| Q6 · What exact files and result rows belong to upgrade and remove? | CP-0010 lines 71 and 78, Onboarding §2 lines 85–87, ALG-12 lines 188–194, and Contracts §§8/10 specify behavior but leave manifest retirement, pruning, change-list order, installed-version mismatch handling and branch-rule reminder text open. | Obtain upgrade targets from the installed release, retain the adoption level and user policy, replace only owned content, and classify changed paths as created/replaced/kept. On successful removal, retire the active and pending installation manifests and remove empty managed directories. List the kept roots and user edits deterministically and publish the reminder wording for a known branch rule. |
| Q7 · How is an interrupted plan replayed? | ALG-12 lines 182–187 specifies the pending file, per-write hash checks and a rerun. The plan layout, old/new hashes, already-applied detection, fault points, stale-plan error code and precise resume output are absent. | Give the pending file its own versioned schema. Store prior and intended bytes/digests per write plus progress. On restart distinguish already-applied, unchanged and divergent content before finishing. Refuse divergent values with a dedicated finding and keep the plan inspectable. Test every durable checkpoint using the same fixtures. |
| Q8 · Which Windows host settings receive the wrapper? | Contracts §10 lines 148–158 requires `cmd /c` in local settings when needed, while ALG-12 line 181 confines planned/recorded repository paths. Host detection, profile path, argv split, whether local changes enter the repo manifest and upgrade ownership are unspecified. | Publish per-host descriptor values and entry formats. Keep the committed native command identical on all platforms. Authorize profile writes through a separately confined host adapter, use an injected profile root for tests, and track its owned values in the local profile instead of the shared repository manifest. |
| Q9 · Which CI byte edits follow report consent and reusable fallback? | CI §2 lines 65–81 permits reporter edits with consent, gives existing jobs a step ID if needed, and selects Tenet's workflow for reusable jobs. No generated ID, collision suffix, consent defaults for `--yes`, or file/text example for a reusable caller is pinned. The services case uses the existing-report route and must retain its topology. | Preserve existing IDs and all services. Use `tenet-tests` as a synthesized step ID with a deterministic numeric suffix for collisions. Ask separately before editing a user's reporter step. Make `--yes` default to the generated workflow when consent is absent. Publish original and modified examples including a matrix, services and a reusable caller. |
| Q10 · What is the non-GitHub install plan? | CP-0010 line 75 promises a plain explanation and no card. CI §3 line 113 says the recorder is always written. The preflight reason, capability level, whether GitHub files are emitted, and exit semantics for a supported local-only setup are open. | Install local policy, manifest, lock and host entries on unsupported forges. Omit GitHub event workflows when the remote is unsupported. Report a successful local-only setup and a stable advisory code with the wording that proof cards require the supported forge. |
| Q11 · How does doctor represent checks and fresh-clone availability? | CP-0010 lines 71, 74 and Contracts §8 lines 120, 128 name checks and fields. Their names, order, severity, probe read scope and exact details for a missing lock/workflow or valid vendored clone are undecided. | Publish ordered check IDs for `node`, `git`, `ssh`, `gh`, `lock`, `workflows`, with ok/warning/failure and stable details. Distinguish an optional missing tool from an invalid installation. Verify the vendored kit locally against the lock and pin the expected clone result. |
| Q12 · Which code and exit describe missing executables and locks? | CP-0010 line 75 specifies exit 3 for no Git. Contracts §13 line 177 and Messages lines 29–32 cover old Git and a non-repository, without an exact missing-executable variant. CP-0010 line 71 requires a lock check, but no approved missing-lock finding/exit is listed for doctor. | Add an environment code for a missing Git executable at exit 3. Keep `TN-ENV-NOT-GIT` for a non-repository. Add a canonical missing-lock code and decide whether doctor remains advisory at exit 0 for that case. |
| Q13 · What state is visible after refusals or cancellation? | ALG-12 lines 181–187 specifies rejection codes for path escape and different created content, plus a plan on hash drift. It does not pin which previous writes or manifest remain, the drift code, or the cancellation exit. | Run static path and collision checks before touching files. When execution has begun and a digest changes, stop before the divergent write, retain the pending plan and return a named finding with the plan. Treat a declined preflight as exit 0 with an explicit cancelled result and the unchanged tree. |
