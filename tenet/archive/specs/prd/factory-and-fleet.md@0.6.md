# Tenet product requirements: factory, fleet and operations

> Level L1 · Version 0.6 · Part of [prd.md](../prd.md), split out under the rollover rule (tech spec §5) · Status: **draft, awaiting the Owner's approval** · Budget: 8,000 tokens

**Context card.** Requirements for declaring and governing the factory itself (§4.11) for fleet-wide work, review capacity and operations (§4.12), and for assurance and code health (§4.13). Column meanings, status values and guarantee levels are as in [prd.md §4](../prd.md#4-requirements). IDs are global and never reused.

## 4.11 Factory definition and operation

| ID | Requirement | Serves | Release | Guarantee | Status |
|---|---|---|---|---|---|
| R-120 | A **factory definition** declares workers (role, agent definition, model or harness, skills, tool servers), triggers, environments (image, setup, network allowlist, secrets allowed per worker), identities, routing, channels, scorers and comparison suites. ## 4.13 Assurance and health

| ID | Requirement | Serves | Release | Guarantee | Status |
|---|---|---|---|---|---|
| R-170 | **Continuing obligations.** The proving cases of every built requirement are protected; replacing or retiring one needs a forge-verified decision or evidence that the replacement is equivalent; a change touching an area keeps current evidence for that area's built obligations | V-P17, V-M10 | 0.1.0 | enforced* | proposed |
| R-171 | Each acceptance item states its claim class (functional, compatibility, non-functional, health, safety-security, outcome), method and pass rule (binary, baseline-relative or probabilistic); the definition template includes a worked example and two prompts: which requirement a property captures, and what would make it true but wrong | V-P2, V-V5 | 0.1.0 | — | proposed |
| R-172 | A distinguishing check's baseline run must fail with the expected failure (assertion or property ID); a harness or infrastructure failure is inconclusive | V-P2 | 0.1.0 | enforced* | proposed |
| R-173 | Measurements may compare against a baseline: `baseline_value`, `rule` (gte, lte, no-regression, max-delta, relative-pct), `scope` (diff-lines, touched-files, area, repo) and optional `confidence`; benchmarks report samples and confidence, never a single run | V-P17, V-M5 | 0.1.0 | — | proposed |
| R-174 | One list of **verification methods** (static, health-ratchet, unit, integration, contract, e2e, property, fuzz, mutation, differential, simulation, model-check, proof, benchmark, holdout, visual-runtime, review, production-observation) and **evidence strengths** (generated trials, bounded model checking with timeout as unknown, machine-checked theorem, sampled or proved correspondence to the implementation) in the core; packs set, per lane, which methods satisfy each claim class (M2) | V-V4, V-P12 | 0.1.0 (core); M2 (minimums) | — | proposed |
| R-175 | **Health indicators and ratchet.** Declared, tool-neutral indicators per area (for example complexity, duplication, architecture violations, dead code and stale flags, type coverage, test-suite time and flake rate, docs referring to code that no longer exists); the verify gate refuses deterioration on the touched scope compared with the target's latest baseline unless a forge-verified `accept-health-regression` decision covers it; improvements on main raise the baseline; adoption records existing problems as the baseline | V-P17, V-M10 | 0.1.x | enforced* | proposed |
| R-176 | Architecture rules (layers, forbidden dependencies, cycles) are pinned, protected checks with fix hints, counted as health indicators | V-P17 | 0.1.x | enforced* | proposed |
| R-177 | **Checks have a lifecycle**: each pinned check names an owner (0.1.x); at M2 it also has a known-bad fixture it must keep failing, a noise budget (overrides, quarantines, findings marked not useful) and retirement when its cost exceeds its benefit | V-P8, V-P2 | 0.1.x; M2 | detected | proposed |
| R-178 | **Durability**: the share of a change's lines rewritten or reverted within 30 days, by agent definition and work type | V-M10, V-M5 | 0.1.x | — | proposed |
| R-179 | **Proof evidence** names the prover and version, the theorem statement's hash (matching the approved definition), the obligations discharged, and an audit of what the proof relies on: no escape hatches, axioms within an allowlist, no new unsafe code or foreign-function bypasses; the red-team suite covers escape hatches, invented axioms, weakened theorems and bypasses | V-P2, V-B7 | schema 0.1.0; rules M2 | enforced* | proposed |
| R-180 | **Simulation and differential evidence** carry seed, fault profile, steps, properties checked and a replay command, or reference, generator, cases and divergences; seeds must replay deterministically | V-P2 | schema 0.1.0; M2 | — | proposed |
| R-181 | Configuration, data and feature flags are subjects with the same risk and rollout rules as code; a change to them with a runtime effect is never express by default | V-V5, V-B6 | names 0.1.0; 0.1.x (express); M2 | enforced* | proposed |
| R-182 | When only some tests run, the receipt records eligible, selected and skipped tests, and a periodic full run reports what selection missed | V-P2, V-B8 | M2 | detected | proposed |
| R-183 | Audits ask whether a maintainer would merge the change as is, with three reasons (broken functionality, breaking other code, quality) | V-M2, V-M10 | M2 | — | proposed |
| R-184 | **Cost of the next change**: similar tasks in the same area compared over time, plus occasional sampled next-change exercises | V-M10, V-M7 | M2 | — | proposed |
| R-185 | Tenet's own evaluator is verified in stages: property tests over generated event histories (same verdict in any arrival order; evidence for one subject never satisfies another; late evidence never justifies an earlier decision; quarantine never makes a missing obligation look satisfied) in 0.1.0; bounded model checking of conflict, late-evidence and quarantine sequences at M2; machine-checked proofs optional later | V-P9, V-H3 | 0.1.0; M2 | — | proposed |
