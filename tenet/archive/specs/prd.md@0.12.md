# Tenet product requirements

> Level L1 · Version 0.12 · Status: **draft, awaiting the Owner's approval** · Serves [vision.md](../vision.md) · Normative standard: [kit/TENET.md](../../kit/TENET.md) · Catalog: [prd/catalog.md](prd/catalog.md) · Tooling: [prd/tooling.md](prd/tooling.md) · Decisions: [prd/decisions.md](prd/decisions.md) · Budget: 9,000 tokens · Previous version: `archive/specs/prd.md@0.11.md`

## 1. Scope and positioning

**Tenet is a ready-to-use spec-driven development system for software factories, built on an open standard: agents build what you meant, and you can see that they did.** Intent is written in levelled specifications that people own and agents work from; every change traces to them; changing them is itself governed (§4.0); and "done" is proven against them with evidence agents cannot fake. It ships as a working toolkit that any coding agent, any model and any engine that works through pull requests can use as-is (a command, a CI workflow, agent skills and a local MCP server, templates, reference agents), built on that spec process, a small kernel of seven primitives and one gate rule that makes it checkable (§4.1), and packs. Tenet governs the work; agents and engines do it. Out of the box, an optional reference runner chains the shipped agents through the agent tool the user already has, so the lifecycle works without an outside factory; larger factories plug into the same contract (DEC-52). Every other feature is a standard claim, evidence kind or decision listed in the [catalog](prd/catalog.md). Spec tools, trackers, orchestrators, factory platforms, hosts and dashboards keep their jobs and read and write Tenet's records; tools that draft per-change specs feed the ladder rather than replace it. **Adoption is progressive** (tooling §3): projects start where nothing blocks, and each rule earns the right to block on evidence.

| In scope | Out of scope |
|---|---|
| The kernel, its rule IDs and its versioning | A hosted service, dashboard, database or account system |
| Packs: lifecycles, standard claims, reference agents, skills, loops, criteria, templates | Running models; Tenet's own tooling never calls one |
| A deterministic CLI and SDK; a CI verifier | A scheduler, dispatcher service, fleet manager, issue tracker, analyzer, prover, sandbox or context graph of its own |
| A minimal, optional **reference runner** that executes the shipped loops through the user's own agent host (R-224) | Running models itself; competing with factory platforms, which plug into the same adapter contract |
| A factory definition Tenet validates, records and governs | Executing it (engines and platforms do this) |
| Bindings to forges, hosts and engines through open contracts; a conformance kit | Certifying third parties; paid support |

**Assumptions.** The kernel needs a content-addressed, signable history; git is the reference binding, and records scale in three tiers up to an external append-only store (catalog R-167). The first forge binding is GitHub. Configuration has two planes: `tenet.yaml` (policy) and the optional `factory.yaml` (execution).

**What Tenet can and cannot tell you** (DEC-49). Every result belongs to one of four classes, and the card, board and documents say which:
- **Checked by Tenet:** records, digests, schemas, citations that resolve, which named checks ran on which commit and what they reported.
- **For you to judge:** whether a test is adequate for its item, whether a drafted statement is right, what a blessing covers. Tenet shows what you need and records your decision.
- **Depends on your agent or host:** whether an agent reads context, follows skills or stays away from the Owner's credentials. Tenet states the host's capability level (tooling R-222).
- **Not done by Tenet:** running agents, engines, dispatch and fleets. Tenet declares, records and gates them.

No result says "proven", "authorized" or "automatic" beyond its class.

**Relationship to other repositories.** Tenet for Copilot (`tenet-copilot`) is an implementation that will declare conformance. Torus is the first subscribing project after this repository.

## 2. Users

| Persona | Needs | Primary deliverables |
|---|---|---|
| **Owner** (one person or a team with named decision rights) | Write intent once at the right level; a useful result in ten minutes and nothing blocked until they choose; decide only what needs them; trust what the floor says | Spec templates and ladder, `minimal` pack, CLI, CI verifier, board |
| **Maintainer** | Know which earlier promises still hold and that the next change stays affordable | Continuing claims, health ratchet, board |
| **Factory operator** | Declare the factory, see readiness and cost per outcome, change it on evidence | Factory definition, campaigns, metrics |
| **Agent** | The specification sections that apply, an unambiguous assignment, the skills for its station, a way to propose results that the tooling accepts or refuses | Agent definitions, skills, assignment and result contracts, SDK |
| **Implementer** | Seven primitives, one gate rule, stable schemas, conformance per claim | Kernel, schemas, conformance kit, catalog |
| **Steward** | Propose, test and release changes safely | This repository run under its own rules |

**First adopter.** A maintainer who already delegates real changes to coding agents, has CI, and regularly has to reconstruct whether an agent's "done" is true (tested in CP-0016).

## 4. Requirements

Status (`proposed`, `approved`, `built`, `reported`) is this repository's own planning column until CP-0054 converts its specifications to the R-210 format. **Guarantee** is the strongest level a requirement may claim in host-driven mode: `enforced`, `enforced*` (only while the trust assumptions hold as observed or attested, R-110; rules block only in `enforce` mode, tooling R-215), `detected`, `advisory`, or `—`. `0.1.x` means a point release after 0.1.0. Standard claims, evidence kinds and decisions are in the [catalog](prd/catalog.md).

### 4.1 The kernel

| ID | Requirement | Serves | Release | Guarantee | Status |
|---|---|---|---|---|---|
| R-200 | **Seven primitives, one container and one gate rule.** Subject, Actor, Claim, Evidence, Decision, Event and Policy are the only normative record types; the work item (packet) groups the claims, evidence and decisions for one intent. Every other record (lease, run, assignment, result, escalation, ledger entry) maps onto them (tech spec §3.2). **Gate rule:** a transition is allowed when every applicable claim is satisfied (by fresh evidence at the required strength, or, for an approval claim, by a fresh `approve` at the required proof strength) or waived (by a fresh `waive` where waiving is allowed); nothing else advances work | V-P2, V-P4, V-V4 | 0.1.0 | enforced* | proposed |
| R-201 | **Subjects** are content-addressed (`{kind, digest}`); their kinds are pack data (git tree, file set, section and area in 0.1.0; artifact, deployment, configuration, data, flag, platform object and multi-repository later); a claim, evidence or decision is fresh only while its subject's digest is current. A `git-tree` subject covers code only; check inputs (definition, runner image, lockfile) are recorded on the evidence, so every check and decision on one commit share one subject (ALG-01) | V-P2, V-B9 | 0.1.0 | enforced* | proposed |
| R-202 | **Claims** state what must hold: a **selector** (`station`, `lane`, `work_type`, `paths`, `areas`; globs and enums), class, accepted methods (any one satisfies), pass rule (binary, baseline-relative or probabilistic), lifetime (`packet` or `continuing`), owner and whether it may be waived. Several claims are all required. **Applicability:** policies only tighten and the most restrictive requirement wins; a continuing claim applies when a change touches its paths or the dependencies its area declares (the whole area when none are declared); applicability that cannot be computed refuses with a reason | V-P2, V-P9, V-M10 | 0.1.0 | enforced* | proposed |
| R-034 | **Evidence** is an observation about a subject: kind (check, measurement, attestation, observation, review, proof, simulation, differential), method, the claims it addresses, the cases expected, executed and passed, result, producer, input digests and, for observations, `valid_until`. **Strength has two ordered axes:** provenance, who produced the evidence (local < CI < CI with trust observed), and independence, who wrote the check relative to who wrote the change (`self`, the claimant's own run, never satisfies < `same-definition`, a check written in the same change < `different-definition`, a check written or pinned by a separate agent < `different-model-family` < `person`); a missing value counts as the lowest. Methods are not ranked: a pack lists which methods are admissible for each claim class. Policy sets a minimum per axis by claim class and lane. Evidence comes only from checks pinned in the target's policy; each method has a completion rule; a suite finding none of its expected cases is inconclusive | V-P2, V-M2 | 0.1.0 | enforced* | proposed |
| R-203 | **Decisions** have five kinds: `approve`, `waive`, `choose` (an option of a request), `delegate` (a right, with expiry) and `resolve` (a conflict). Every named decision in the catalog is one of these. **A `waive`** names its claim, scope, reason and expiry (an expired waive re-blocks); the actor whose change broke a claim, or an agent acting for them, cannot waive it; below `verify` a self-waive is allowed and labelled `self-waived`; claims marked unwaivable (the trust surface; safety and security claims in the deep lane) cannot be waived: an evidence claim must be met by evidence, never by an approval, and a trust-surface change also needs a `change-policy` approve; retiring a continuing promise is an `approve` by its owner, never a waive | V-V1, V-P1 | 0.1.0 | enforced | proposed |
| R-101 | **Decisions carry proof**, in strict order `person-present` > `forge-verified` > `key` > `channel`; the policy's proof table sets what each decision needs (default `forge-verified`; `person-present` only at the `assure` level, for policy, permission, vision and deep-lane release). `forge-verified` means *attributable to the decision-maker's forge account*: it counts as enforced* only where trust assumption 4 is attested (R-110), otherwise as detected, and the forge's two-factor status is recorded as `enforced`, `not-enforced` or `unobservable`. A native review approval binds the reviewed commit and is the primary path; a decision reply (`/tenet approve`, `/tenet pick 2`) binds the **evaluation** the latest proof card showed (its commit, acceptance block, the blessed text of the requirements it implements, and policy) and is refused if any of them changed since that card; naming the evaluation is optional (required at `assure`). Answers bind request, subject, choice, actor and policy version; signatures survive squash, rebase and shallow clones | V-B2, V-P12 | 0.1.0 | enforced at the required strength | proposed |
| R-102 | **Decision requests** are durable: subject, question, options with stop first, recommendation, who may decide, deadline, default stop; delivered on the pull request from 0.1.0. An option that changes scope cannot approve the current subject | V-V1, V-V8 | 0.1.0 | enforced | proposed |
| R-124 | **Actors** are people, agents and services; every run records its actor chain (initiator → agent → subagent → tool) with scope and expiry, credential policy, environment, harness, model, factory-definition version and usage with cost source | V-P11 | 0.1.0 | detected | proposed |
| R-039 | **Events** are the source of truth: one immutable file each, carrying `prev` (the IDs of every event the writer saw as latest, so a `resolve` names both branches), in seven families (`work.*`, `claim.stated`, `evidence.recorded`, `decision.*`, `run.*`, `gate`, `lease.*`); station and holding status are separate fields. Gate events record which pack rule linked each piece of evidence to each claim (the argument). CI replays each changed work item and labels every state change justified, pending evidence (**tentative**: never counted by a later gate; unjustified after a timeout) or unjustified; incompatible concurrent state changes create a conflict a `resolve` settles; gate events record their evaluation instant, so replay is reproducible; forge state and decisions read from forge reviews are recorded by the recorder job (unsigned from alpha.1; signed, as the attest job, from alpha.2) | V-P2, V-P10 | 0.1.0 | enforced* | proposed |
| R-109 | **Policy comes from the target, judged at decision time.** The verifier reads `tenet.yaml`, the lock, packs and the Tenet version from the target line, never from the change; every gate evaluation records the policy, evidence-store and trust-observation revisions it used, and replay uses that snapshot | V-P10 | 0.1.0 | enforced* | proposed |
| R-204 | **Policy declares** which claims apply where (packs, stations, lanes, areas, work types), the proof table, approvals by risk, owners and keys, pinned checks, budgets and the protected claims; projects may only tighten what a pack sets | V-P7, V-P12 | 0.1.0 | enforced* | proposed |
| R-006 | Every kernel rule declares its **guarantee level** per execution mode and the trust assumptions it depends on; the board shows the level in effect for each change | V-P12, V-B8 | 0.1.0 | — | proposed |
| R-030 | Work items get a ULID identity and a 6-character alias; duplicate aliases are refused at merge; every existing `CP-NNNN` stays valid | V-P5 | 0.1.0 | detected | proposed |
| R-031 | `tenet move` appends an event and refuses a move the gate rule refuses, naming each unsatisfied claim and the next command | V-P2, V-H1 | 0.1.0 | enforced* | proposed |
| R-205 | **Minimal valid records.** Each primitive has three to five required fields and everything else is optional with a stated default; a producer conforms at the `minimal` level by writing only those. A record missing a field a claim needs (cases, independence, inputs) is valid but cannot satisfy that claim, and the gate names the missing field | V-V4, V-P7 | 0.1.0 | — | proposed |

## 5. Versioning and release policy

| Change | Version | Subscriber effect |
|---|---|---|
| Wording, clarification, bug fix | Patch | Auto-merge after the conformance check |
| New optional capability; a stricter check conforming projects already pass | Minor | Auto-merge from 1.0; review below 1.0 |
| Changed schema, removed rule, new required gate, any change to authority, permissions, severity or evidence requirements | Major | Waits for a decision-maker |

A release is cut from an `ops` release packet with a `release` decision. **Release gates prove the software works; horizons prove its value.** They are never the same gate.
