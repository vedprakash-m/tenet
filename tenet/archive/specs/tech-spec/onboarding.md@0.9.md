# Tenet technical specification: onboarding, install and upgrade

> Level L2 · Version 0.9 · Part of [tech-spec.md](../tech-spec.md) · Status: **draft, awaiting the Owner's approval** · Budget: 6,000 tokens · Split from `tech-spec.md` §6.5 and §12 under the rollover rule (L-0022)

**Context card.** How a project gets Tenet, how its specifications are drafted and blessed, and how Tenet is upgraded and removed. Implements PRD R-223 and tooling R-020, R-021, R-025, R-051 and R-221; the experience is UX spec Parts 0, 1 and 4.

## 1. Onboarding and blessing (R-223)

<!-- provisional --> **Preflight and inventory.** `tenet onboard` lists what it will read (code, configuration, tests, docs, CI, owners), what it skips (`.env*`, credentials, vendored and generated paths, anything in `onboard.exclude`) and that drafting sends content to the user's own agent and its model provider; `--inventory-only` stops there. It writes `.tenet/onboard/inventory.json` (git-ignored): languages and modules, entry points, routes, commands and schemas it can parse, configuration and flags, tests with names and last results, docs and ADRs with their last-changed dates, CODEOWNERS areas, CI workflows, and the revision it read. A **drafting assignment** (the JSON contract, R-048) points the user's agent to the inventory, the `draft-specs` skill and the size rule: one `intent.md` with five sections below about 20,000 lines of code or with few docs, separate documents above it, per area in a monorepo.

**Draft format.** Each requirement carries its origin and, for `observed` and `documented`, a citation: `[src/retry.ts:40-48]`, `[test: checkout.retry.test.ts › retries once]` or `[docs/architecture.md#retries]`. `asked` statements record that the Owner answered; `inferred` ones are marked and cannot be blessed unedited. A `## Conflicts` list names disagreeing sources; an `## Open questions` list names what only the Owner can settle. Front matter per document: `drafted_from` (revision), and per section `state`, `digest`, `owner`, `blessed_by`, `blessed_at`.

**Checks and blessing.** `tenet check` verifies every citation at `drafted_from` (the file and lines exist; the test exists) and flags statements without an origin. `tenet bless` runs only in an interactive terminal: it walks the person through conflicts first, then each section with its reading time (bless, edit, reject, defer), and writes the states; it refuses to bless a section with an open conflict or an unedited `inferred` statement. From alpha.1 a review action on the onboarding pull request also blesses. A blessed section whose digest or cited sources change becomes `stale` and returns to the blessing queue. Re-running `onboard` keeps IDs, edits, rejections and blessings, and proposes only changes.

## 2. Install and upgrade

`init` runs the preflight (R-020), writes `tenet.yaml`, `tenet.lock`, the `AGENTS.md` block, the CI workflow and the detected hosts' skills and MCP entries, records them in `.tenet/manifest.json` (created files, edited blocks, host entries) and offers onboarding (§1). Existing files are edited only inside marked blocks. Integrity is checked by hash; files are not made read-only. `tenet remove` reverses the manifest, keeps specifications and records, and names any branch rule an administrator must remove. **Upgrade** (0.1.0): update the lock, regenerate the `AGENTS.md` block and skills, report what changed, run `tenet check`; never change the level or start a new rule beyond `observe`. From M4: stage, migrate with a restricted file API, regenerate, swap atomically; classify from structured fields; a scheduled pull request.
