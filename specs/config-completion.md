## 1. Outcome

A user can change a setting in plain words, see the interpreted value and scope and what it changes for work already under way, ask "why <setting>" or "what have I set?", and rely on four properties that are tested rather than assumed: resolution follows PRD §7.4, personal settings never reach a shared file, Tenet never rewrites another tool's instruction files, and saying the same thing twice changes nothing. What cannot be built before the host spike SP-02 (where personal preferences can be written, which instruction file the host loads) is listed as open, with no stand-in.

**Verification:** drive the built kernel on a scratch repository through each example in §4; compare responses and stored documents.

## 2. Current state (inspected 2026-10-24)

## 6. Alternatives considered

| Option | Behavior | For | Against |
|---|---|---|---|
| A. Skill text only | Tell the coordinator to read back and confirm | no kernel change | cooperative only; PRD says never claim more than the mechanism gives; a skipped read-back loses "never touch" strength |
| B. Read-back always, confirm only loosening (this draft) | Kernel returns the read-back; one bound question for loosening | the fidelity risk is highest for restrictions; matches UX "applied at once" for the rest | one new question id; loosening detection must be exact |
| C. Confirm every durable change | One question per project save | simplest rule | contradicts UX §8.1 and CFG-07 "without re-asking" |
| D. Separate preview verb | `inspect` a proposed change, then `decide` | read-only preview | extra call every time; two ways to write |

**Recommendation: B.** For CFG-10: compare as sets (CC-8) rather than sort on write, so the user's order is kept.

## 7. Risks

- Loosening detection misses a case (for example a glob replaced by a broader one). The kernel has no implication solver (`policy.ts` header); a changed glob counts as loosening the old one, so the rule errs toward asking.
- The skill budget is full; a resource file adds loaded tokens against `LOADED_BUDGET` 12,000.
- `config-confirm` adds a pending question that fences dependent mutations like the others; a forgotten question blocks work. It follows the existing `adopt-confirm` pattern (`adopt.ts:82-102`).
- Enforcement labels must stay true as consumers are added (RSC-05): the label comes from one table next to the catalog, tested.

## 8. Assumptions

- A1: "show before saving" is met by a read-back in the same reply for preferences and tightening, and by a question for loosening (UX §8.1 governs the wording).
- A2: Until SP-02, durable preferences go to the project (plan 2026-10-19 decision) and the reply says so rather than "for you in every project".
- A3: `[CFG-03]` coverage by existing tests needs only tags and the gaps in §3.

### 14.1 Exact input and response contract

- Entry remains `decide`, `kind: "config"`, with a live workspace work handle `h`; use the existing pipeline lock, recovery, handle validation and publication. Never mutate state outside it.
- Single form: `target: <catalog key>`, `propose: {value: <JSON>, scope?: "task"|"project"}` OR `propose: {reset: true, scope?: "task"|"project"}`. Exactly one of `value` and `reset` is present; `null` is a value and fails any schema that does not admit it. `reset:false`, extra proposal members and missing proposal are errors.
- Batch form: no `target`; `propose: {settings: {<key>: <raw catalog value>, ...}, scope: "project"}`. Require a nonempty plain JSON object; no per-item envelopes, reset operations or task batches. Values that happen to contain `reset` are validated as setting values, never interpreted as resets. Scope is explicit for batch; reject `settings` mixed with `target`, `value` or `reset`.
- Default single scope is the catalog's first allowed scope, preserving existing calls. Validate scope membership BEFORE either set or reset, even when the override is absent. Reject unknown scopes, `shared_memory` (use adoption), task commitments/executables/integration and unsupported user scope; reset cannot bypass any restriction. Shared policy is never a writable scope here.
- Malformed JSON retains the existing CLI transport result: exit 1, `invalid-input`, before decision dispatch. Reject decoded non-object proposals, empty batches, forbidden envelope combinations and wrong-typed scopes with exit 2 and `restriction-key-unknown`; write no config or config question. A well-shaped envelope with unknown keys or invalid setting subfields instead follows 14.4, with path-specific diagnostics. Do not silently strip unknown fields.
- The only permitted answer map has exactly the current question ID and value `confirm` or `decline`. An absent map means proposal; an empty map, unknown ID/value or unrelated answers is rejected (exit 2, `revision-conflict`). `quote` is not a config input; reject it. `again` retains pipeline retry semantics, never approval semantics.
- Confirm repeats the complete original single/batch proposal and target, plus the matching answer; answer-only confirm is invalid. Decline is answer-only (no target/propose) and cancels only its matching current-work question. Reject decline mixed with a proposal. Validate answer mode before applying any value, even if the recomputed change is now ungated or a no-op.
- Single response keeps `setting`, `scope`, `value` or `reset`, `changed`, and adds `interpreted`; batch response has `settings` (one result per key), `changed`, `interpreted`, `applied` and `rejected`. In partial results `changed` describes persisted configuration, never just a question write; every item has its own changed flag.
- `interpreted` includes normalized operation, requested scope/value/reset, stored override presence before/after, effective before/after, contributions/limits, layer-wide revision, affected work IDs/generations, timing and undo request. Kernel supplies facts; coordinator supplies literal wording. An undo is a new validated proposal, not a bypass or guaranteed restoration of inherited policy.
- Full success/no-op/cancel: exit 0. Preview: exit 3, config unchanged, pending question stored. Rejected/partially applied content: exit 2, `restriction-key-unknown`, diagnostics at every rejected JSON path and explicit applied paths. Stale answer: exit 2, `revision-conflict`, nothing applied. A partial exit 2 is never described as rollback of its reported safe revision.

### 14.2 Equality, classification and D2

- Validate first; invalid content is never a no-op. Compare stored presence separately from normalized value: absent means inherit, explicit default/empty/zero/`auto` remains an explicit source. Adding an override equal to an inherited value changes attribution once; resetting an absent override is a no-op only after scope validation.
- Equality: protected paths are exact-string sets; exclusions union kinds per exact pattern, including repeated pattern entries; required checks group by ID with equivalent definitions deduplicated; `alternatives` are sets; record keys are unordered; command `argv` order is significant. Missing optional fields are not invented; dependency fields use the documented inheritance/default semantics for effective comparison, not to erase explicit source presence.
- Equivalent reapplication preserves stored order/bytes, makes no configuration revision, creates no approval prompt and changes no existing pending question. Non-equivalent same-ID check definitions are conflicts, never equal and never resolved by keeping the first. `comparePolicy`/`stableStringify` are reusable components, not proof of this full equality contract.
- Compute both the local semantic delta and effective before/after from all layers. Every actual command add/remove/replace/reset gates under D2 even if shared precedence masks its effect. Any existing-check definition change gates, including property, tool/invocation, configuration, population, pass and alternatives; removals/resets require confirmation when they loosen or materially change commitments. Compare against every applicable same-ID source, not just the selected local value.
- Other effective loosening/material restriction changes gate under D1; unknown implication (including changed glob text) is not proven tightening. A valid explicit preference or provable tightening applies immediately with read-back. Empty local lists cannot remove inherited restrictions. All-valid batches are atomic: if any member gates, preview the WHOLE batch and persist none until a matching confirmation. D6 is the only partial-write exception.
- Neither preview, confirmation, direct save, reset nor partial save runs commands, changes grants/consents/counters, grants protected-action authority or supplies evidence. Existing validated execution envelopes and gates remain mandatory. A confirmed conflicting definition is still a conflict, not a waiver.

### 14.3 Confirmation identity, freshness and isolation

### 18.4 Launch Phases, Honest Counts and Exactly-Once Settlement
Prepare job: under the lock allocate jobSeq above the durable high-water, bind owner/generation/runId and issued proof identity, and checkpoint allocation before any command can run. Inside guardLaunch's transaction revalidate ownership/cancellation and current execution gates, then fsync starting BEFORE spawn. Spawn synchronously while stop cannot acquire the lock. Affirmative spawn acknowledgment fsyncs launched BEFORE releasing that lock; affirmative OS spawn failure with no child fsyncs no-launch. If any acknowledgment write fails, stop any identified process group and leave starting unresolved. No automatic respawn under the same LaunchKey, even if the process is now gone.
Durable boundaries: prepared without starting proves no launch ONLY because all spawn paths require starting first; starting without a terminal acknowledgment is uncertain; launched proves one invocation of its captured obligation set; no-launch requires positive pre-spawn cancellation/refusal or affirmative no-child spawn failure. PID absence/death, missing temp files, timeout, a killed kernel or run.json starting do not prove no launch. Process liveness may prevent signaling but does not erase a durable launched record.

Uncertain launch cardinality fences dependent new execution, completion and accounting-complete claims. The existing process-stop protocol is still required, but stopping alone cannot resolve a spawn acknowledgment gap. A stale/interrupted run earns no fabricated attempt, failure signature, review round or recheck credit.
