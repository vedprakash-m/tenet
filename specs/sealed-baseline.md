Its rules bind here: **R-A** only failures of a broader check on a recorded starting tree enter the baseline record, never planned reds; **R-B** "pre-existing" requires a complete candidate failure list (`failures.length === counts.failed`); **R-C** the exclusion mechanism needs a verdict input, a `decide` kind and wording; **R-D** a failure at HEAD alone is never pre-existing when the start tree was dirty.

## 1. Outcome

When a broader test suite fails on the candidate, the result says, for those failures, whether they also fail the same way on the starting files (`pre-existing`), did not fail on a run of the starting files (`introduced`), or cannot be classified, with the reason (`classification-unknown`). Nothing is called pre-existing without a completed run on the reproduced starting tree, and nothing is called introduced without a complete starting record. A failure classified pre-existing does not stop the contract as a repeated failure, and once the user excludes it the contract can reach `checked-local`. A second, separate slice lets a check of the committed tree lift the scope from `working-tree-with-your-edits` to `committed`.

**Verification:** real Git repositories and real test processes through `open`, `check`, `decide`, `finish`; a built-bundle scratch run on a repository with a red suite; compare receipts, reasons and headlines with the examples in §5 and §15.

## 15. Revised scope, v2 (supersedes §3 to §13 where they differ)

### 15.1 Slice 1: sealed baseline (specified for build)

| ID | Requirement |
|---|---|
| SB-1 | A *broader check* is the obligation `OB-suite` (`kind: "test"`, no `testFile`). Acceptance, boundary-test, static and e2e obligations are not classified; their failures stay `evidence-failed`. A failing acceptance test inside the suite report appears in the suite's failure ids; it does not exist at the start, so it classifies as introduced. Only candidate-stage runs trigger or read classification; the integrated stage does not (after a base move, other people's changes would read as introduced). |
| SB-2 | The suite receipt carries `failureIds` (max 200 entries, each at most 300 characters): `<file>::<test>` followed by `\u001f<kind>:<sig>`, where `sig` is a short hash of the first message line with digits replaced by `N`. A file that failed to load uses its path as the test. The list is complete when its length equals `counts.failed`. Comparison of test identity uses the part before `\u001f`. |
| SB-3 | After the flaky reruns, if `OB-suite` still fails (recomputed in `execute` with `failedAmong` over the final rerun facts), the call is a candidate-stage full run, and no sealed record exists, `execute` runs the same test command on the reproduced starting tree in the same call. It does not run when the first run took over 2 minutes, when the candidate run was inconclusive or the first run timed out, or after a kill; its timeout is `min(10 min, max(30 s, 2 × first run))`. |
| SB-4 | Starting tree = tree of `start.head`; minus paths the exclusion policy forbids reading (globs expanded to tracked paths); plus each `start.dirty` file whose current working blob equals its recorded blob (copied with its mode, then re-hashed in the copy); deleted-at-start paths removed. Declared tests and scaffolding of this contract are deliberately not added (they did not exist at the start). Any mismatch is "start changed". |
| SB-5 | The materializer never writes to the user's Git directory, never runs a filter or hook, never touches the workspace or index, stashes or resets nothing, removes only what it created, and returns a `realpath`'d root outside the workspace and `.tenet/`. The sealed directory is deleted at the end of `execute`. |
| SB-6 | `WorkContract.sealedBaseline` is `{ status: "recorded", startId, failed: string[] ≤200, complete, at } \| { status: "unavailable", why, tries }`. A completed run (ran, no timeout, valid report, workspace digest unchanged) records. A transient failure (timeout, invalid report, workspace moved, mkdir or checkout error) stores `unavailable` with `tries` and is retried once more; permanent reasons (SB-10) are decided before any process, cost nothing, and are recomputed each check. A `recorded` baseline is reused by later checks without a rerun. |
| SB-7 | One pure function `classify(receipt, baselineState)` in `core/baseline.ts` returns `pre-existing` (receipt ids complete and every identity-plus-signature in the record), `changed` (a test fails at both with a different signature: unknown with that reason), `introduced` (record complete and an identity absent from it), or `unknown` (record absent, incomplete or unavailable, with the reason). It is the only place the rule lives; `core/verdict.ts`, `account`, `evidenceReasons` and `nextStep` call it. |
| SB-8 | Verdict: pre-existing and not excluded blocks (`baseline-failure-not-excluded`); excluded is a note (`baseline-failure-excluded`). Unknown or changed blocks with `classification-unknown`; excluded unknown is a note with the new code `baseline-failure-unclassified-excluded`; `treated` (answer `fix`) reads `evidence-failed`. Introduced is `evidence-failed`. `continueRequired` is unchanged: it keys on `evidence-failed`. |
| SB-9 | Accounting: a candidate full run whose failing receipts are all pre-existing records no attempt and no failure signature (its launched checks still count). Unknown and introduced record both. `passedAll` and the review-manifest issue treat a failing broader receipt that is pre-existing and excluded as passed. `evidenceReasons` emits the classification's reason, not `evidence-failed`, for pre-existing and unknown. The sealed run counts one launched check. |
| SB-10 | Permanent "unknown" reasons, each decided before any process: no writable temp or a materialization error; `git.mode` not `git`; `start.head` absent, unborn or gone; submodules, sparse checkout, a linked worktree, or a tracked symlink leaving the tree; a start-dirty entry that is a symlink or excluded; a filter named by the start tree's `.gitattributes` and configured; the start tree above 50,000 files or 500 MB; `sealed-deps-unavailable` per finding 7; "start changed". |
| SB-11 | Question and decision: `finalizeCheck` returns the aggregate question `baseline-failures` (exit 3, in `state.pending`) when a failing suite is pre-existing-not-excluded, unknown or changed. New decision kind `baseline-failures` (`decisions/baseline.ts`): answer `exclude` requires the user's quote and records `exceptions: [{kind: "baseline-failure", ids, reason: quote, at}]` (cap 200); answer `fix` records `treated`. Bound to `factsHash`. After either answer the next step is `check`; the recheck reuses the record, issues no sealed run, and issues the review manifest if all else passes. |
| SB-12 | Readers by stage: one helper `candidateReceipts` (stages `candidate`, `integrated`) is used by `fresh()` and the stale-versus-missing test in `verdict.ts`, `latestByOb` in `finish.ts`, `handoff.ts`, `core/review.ts` (`slice(-12)`). Sealed receipts are kept for `inspect` only. |
| SB-13 | Adapter advances to `node-ts@11` (new receipt content). Stored receipts go stale once. |

| ID | Requirement |
|---|---|

### 15.4 Wording (proposed, for UX backfill)

- Pre-existing, not excluded: "These tests also fail on a run of your starting files: `dates.test.ts` (2). Leave them out of this work, or fix them as part of it?"
- Pre-existing, excluded: "Fails before and after my change: `dates.test.ts` (pre-existing, excluded)." (UX line 397, unchanged)
- Introduced: "These tests weren't failing this way on a run of your starting files: …" New tests: "New tests that fail: …"
- Unknown or changed: "Couldn't tell whether `dates.test.ts` failed before: <reason>. Leave it out, or treat it as mine to fix?" Reasons: "a file you had edited at the start has changed since", "it fails on your starting files, but differently", "the run on your starting files did not finish", "more than 200 tests fail", "a Git filter would have to run", "dependencies could not be shared safely", "no writable temporary folder".
- Excluded unknown: "`dates.test.ts` fails; you left it out. I couldn't show it was failing before."
- Committed with human files present: headline "Checked locally (`checked-local`), committed on <branch>"; Limits: "your 2 uncommitted files are not in the commit; the commit alone was re-checked." (keeps the human-file mention that `headline()` drops for scope `committed`.)
