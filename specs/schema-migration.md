## 1. Outcome

When Tenet is updated while a project has state, the user is never silently moved between versions: a contract pinned to the old versions stops at its next boundary, says what changed, and continues only after an explicit reconcile; an older state document is migrated only after a preview and with a restorable backup; a state document written by a newer kernel is never rewritten by an older one. Records that cannot be understood are diagnosed, not reset.

**Verification:** real stores and real kernel processes; compare responses, stored documents and backups with the examples in §5.

## 2. Current state (inspected 2026-10-24)

- Only schema version 1 exists (`SCHEMA_VERSION = 1`, `core/schemas.ts:7`), so no migration has ever been needed or written.
- The store refuses any marker whose `schema` differs from the running kernel's, older or newer alike, with `unsupported-record` (exit 4, "needs a compatible kernel or an approved migration; it was not quarantined", `adapters/store-fs.ts:221`). No code path produces the reason `migration-needs-approval` (declared in `core/reasons.ts:76`).
- There are no upcast functions, no `state.v<N>.bak`, no read-only mode for a newer document. `state.prev` is the only older copy and it exists for crash recovery.
- A contract records `pinned: { tenet, schema }` when it is created (`core/state.ts:64`, `core/schemas.ts:296`). Nothing ever compares it with the running kernel, so the reason `version-changed` (`core/reasons.ts:77`) is never produced. The technical specification's `pinned` also lists `recipe` and `adapter` (tech-spec line 780); the code records neither.
- The adapter version is already part of the toolchain fingerprint, so a changed adapter makes old receipts stale, but nothing tells the user or pauses the contract.
- `State` is a strict object with an optional `_ext`; unknown top-level fields are refused at parse, not preserved.

## 4. Design

- **Pinning.** `WorkContract.pinned` becomes `{ tenet, schema, adapter, recipe? }`, all optional-compatible for existing documents (a missing field reads as "unknown", which is treated as unchanged for that field so existing contracts do not all pause once; the first reconcile fills it). `newContract` takes the adapter and recipe versions from the stack and project state.
- **Detection.** A pure `versionDrift(pinned, running)` in `core/` returns the changed fields. The pipeline's envelope step (which already resolves the contract) raises `version-changed` before the verb runs, except for the verbs that may proceed (VM-2). Because it sits in the shared envelope it cannot be bypassed by a front-end.
- **Reconcile.** `decide version-reconcile` (a new kind in the registry) applies the choice and re-pins. It writes one line to the handoff.
- **Migration registry.** `core/migrate.ts` holds an ordered list of `{ from, to, upcast(doc) }` pure functions (empty today, since only schema 1 exists) and `migratePath(from, to)`. The store reads the marker and state schema, upcasts in memory, and distinguishes lower, equal and higher. The `migration-needs-approval` response carries a preview built from a pure `describeMigration`. The backup is written with the existing synchronized private-file writer before the new document is published.
- **Read-only mode.** The store gains a `readOnly` condition surfaced to the pipeline, which refuses mutating verbs with the reason and still serves read-only views.
- **Test seam.** The store accepts an injected migration list so tests can exercise the whole flow with a fake `1 → 2` upcast without shipping a real second schema.

## 6. State and contract changes

- `pinned` gains optional `adapter` and `recipe`. Both schemas are non-strict at the nested object, so older readers ignore the new fields.
- New files in `.tenet/`: `state.v<N>.bak` (one per migration), counted against the storage budget and never evicted while the migrated schema is current (plan §12.10).
- New decision kind `version-reconcile`; new response states `version-changed` (exit 3) and the read-only condition.
- No change to the journal format, receipts or the marker beyond its existing `schema` field.

## 7. Alternatives

| Option | For | Against |
|---|---|---|

| B. **Recommendation: B.** LFC-03 is a visible, user-facing safety behavior that can be completed and proven now; the migration machinery is cheap to build against a fake migration and expensive to build under release pressure.

## 8. Risks

- A version check in the shared envelope pauses every contract once after a normal update. The `unknown`-field rule (E4) limits that to real changes; a kernel patch release still pauses contracts once, which is the specified behavior ("pause at the next boundary") but may feel noisy. Decision D2.
- The read-only mode touches the pipeline. It must refuse mutating verbs in one place.
- The injected migration is a test seam in production code (an option on the store); it must be unreachable from the command line.

## 9. Assumptions

- The kernel version is available at run time (`version.ts`) and the adapter version from the stack's fingerprint.
- Users update the plugin through the host; Tenet cannot observe an update except by seeing different versions on the next call.

## 10. Acceptance criteria

1. E1 to E14 pass with real stores and processes.
2. No path rewrites a document written by a newer schema.
3. A migration never publishes before its backup is durable.
4. `npm run ci` within module budgets (increases above 1% raised for decision); built-CLI scratch run; plan, changelog, TS §7.7/§15.3 backfill.

## 11. Decisions for the owner

- **D1.** Option B (recommended), A or C.
- **D2.** Which version changes pause a contract: any change in kernel, schema, adapter or recipe (recommended, as specified), or only schema, adapter and recipe (patch releases of the kernel alone do not pause).
- **D3.** `state.v<N>.bak` retention: keep until the next migration (recommended), or delete after N successful mutating calls.

## 13. Revised scope, v2 (supersedes §3 to §11 where they differ)

**1. What is built now: LFC-03 only.** Version pinning and the pause. Migration (VM-4 to VM-9, LFC-04) is deferred to its own spec, triggered by the first real schema change; the reviewed design notes in §13.4 are the starting point. The injected-migration seam, `state.v<N>.bak`, read-only mode and rollback are not built.

**2. Pinning, detection and the order.**
- `pinned` becomes `{ tenet, schema, adapter }`. New contracts record all three. `adapter` comes from a new `stack.adapterVersion()` (the `ADAPTER` constant). A missing `adapter` on an existing contract is back-filled silently at its first call. Recipe is not part of drift.
- Drift is a pure `versionDrift(pinned, running)` returning the changed fields: `tenet` compared as `major.minor` plus any pre-release tag; `schema` and `adapter` compared exactly. It is symmetric: an older kernel on a newer pin also drifts (a downgrade is named as one).
- Order in the plan step: parse, `fence` (pending-question rules, `work-busy`), then the version check, then the verb. For `open --resume` the contract is selected by its existing selector and checked the same way. Read-only verbs and `inspect` do not stop; they add a non-blocking `version-changed` note for the contract in view.
- When it stops a call, it returns exit 3 with a question bound to the drift (`version-reconcile`), not a stored pending question.
- Allowed while paused: `stop`; `inspect` and other read-only verbs; `decide` kinds `version-reconcile`, `abandon-confirm`, `takeover-check`, `repair-lock` and the quarantine answers. Every other verb and decision is refused with `version-changed`.
- `decide version-reconcile` answers `continue` (re-pin to the running versions; evidence keyed to a different adapter is already stale and reruns; grants, locks, counters and intent unchanged) or `stop` (parks the contract). It re-pins only the contract it names. Other contracts pause independently on their next call. Creating a new contract on a project with paused ones is allowed and pins the new versions.
- A check already running is never interrupted; the pause applies to the next call (the existing `work-busy` fence already refuses calls during a run).
- Recovery runs before the check, as today; it only completes effects already recorded and checks their postconditions.

**3. Examples (all in `version-pin.test.ts`, real stores, a stack wrapper reporting other versions).** E1 a contract pinned under one adapter version, called by a kernel reporting another: `version-changed` with one question; `inspect` and `stop` work. E2 "continue" re-pins; the next call runs; grants, locks, counters and receipts unchanged; old receipts are stale and a check reruns. E3 a real check is running when versions change: it finishes and publishes; the next call pauses. E4 an older document with no `adapter` is back-filled, not paused. E5 `open --resume` on a drifted contract pauses. E6 a read-only verb (`inspect --view status`) returns a non-blocking note and is not refused. E7 a pending takeover question and a drift together: the takeover answer is accepted, then reconcile. E8 a downgrade (older kernel, newer pin) is named a downgrade and pauses. E9 a handle of a parked contract after another contract reconciled: still pauses for itself. E10 `open` of a new contract on a project with a paused one succeeds and pins the running versions. E11 a store whose marker has a higher schema is never written by this kernel (no `.gitignore`, journal repair, eviction or temp sweep changes anything). E12 patch-only kernel change (`0.1.0-m0` to a patch of the same major.minor) does not pause.

**4. Migration design notes (recorded for the later spec; not built).** Step order: durable backup, directory sync, marker, state, directory sync, with a recovery rule for each marker/state mismatch (marker N and state N-1 resumes; marker N-1 and state N rolls the marker forward; never fall back to `state.prev` on a schema mismatch). Upcast `state.prev` too; version the parsing in `publishState` and `prevRevision`. An upcast never changes `revision`. Read-only is enforced inside `FsStore.transaction` and `acquire` with an allow-list, covering the store's own writers (`repairLogTail`, `ensureMarker`, `evict`, `purge`, `cleanTemp`, `sweepTemp`, `repairLock`). Read the raw schema before parsing and never fall back. Rollback is a `decide` run by the new kernel using `migratedAtRevision`, or a documented manual restore. `decide forget` must scrub backups. Nested plain `z.object`s strip unknown keys on every publish today; the migration spec must list each record type's unknown-field behavior. The test seam must inject the target validator and be unreachable from `wire.ts`.

**5. Size and state.** `Obligation`-level nothing changes. `WorkContract.pinned` gains `adapter` (non-strict, optional). Estimated growth: about 30 lines in `core/` (`versionDrift`, semver compare), 45 in `pipeline-mutate.ts`/`open.ts`/`decisions` (check, resume path, `version-reconcile`, read-only note), 3 in the stack port and node-ts. ## 15. First Real Upgrade Scope (Owner Decision 12, 2026-10-24)

### 16.1 Current Boundaries and Required Changes

- [store-fs.ts](../packages/kernel/src/adapters/store-fs.ts): `read()` validates the marker, tries primary then previous, and applies `recoverAccounting()`; recovered previous uses `recoveredState()`. `readJson()` currently collapses malformed/unreadable into null. Migration admission must retain those distinctions and raw schema before any validator/fallback.
- `acquire()` currently creates/chmods paths before its schema refusal; `transaction()` then repairs the log tail. `publishState()` increments revision, appends accounting, rotates previous by hard link and publishes primary. None is a pure-upcast writer. `repairLock()` removes dead identities outside `acquire()`.
- `reduceLog()` writes `summaries.json` first, keyed by the old log hash, then replaces `log`; `prevRevision()` uses the current validator. [journal-reduce.ts](../packages/kernel/src/core/journal-reduce.ts) protects unresolved pairs, recent records and accounting at/above the previous revision. Preserve that recovery horizon and summary deduplication.
- [budget.ts](../packages/kernel/src/core/budget.ts) checkpoints budget deltas and sequence high-water marks; `recoverAccounting()` can raise counters/generations but reconstructs neither authority nor evidence. Migration must not invoke it silently to alter source bytes or declare incomplete accounting verified.
- [pipeline.ts](../packages/kernel/src/pipeline.ts) routes read-only calls without a transaction; [pipeline-mutate.ts](../packages/kernel/src/pipeline-mutate.ts) runs `preLock` before acquiring, then effect recovery before version gating. Ordinary migration decisions cannot enter that path first.
- [quarantine-fs.ts](../packages/kernel/src/adapters/quarantine-fs.ts) journals imported-entry identities before moves, then publishes fresh ownership; [quarantine.ts](../packages/kernel/src/decisions/quarantine.ts) offers metadata review, not authority restoration. A migration manifest is not an ownership marker.
- [cleanup.ts](../packages/kernel/src/decisions/cleanup.ts) removes temporary run files, not `.tenet`; [forget.ts](../packages/kernel/src/decisions/forget.ts) publishes twice through the pipeline and calls `purge()` on lesson text/quote in temporary files. It does not currently handle migration copies, archives or blobs.

### 16.2 Proposed APIs and Schema Delta

Extend the existing Store port in [types.ts](../packages/kernel/src/ports/types.ts), not the number of ports: proposed `compatibility()` (read-only admission/snapshot), `previewMigration()` and `migrate({factsHash, answer, quote})`; `previewRollback()` and `rollbackMigration({factsHash, answer, quote})`. Add proposed decision kinds `schema-migrate` and `rollback-migration`, dispatched before `preLock`, ordinary transaction recovery or contract envelopes. They are workspace decisions: no live work handle is needed. These APIs/kinds do not exist today; `version-reconcile`, `repairLock`, `transaction`, `read`, `publish` and `purge` do.

Proposed internal pure `upcastSchema1()` and explicit schema-1/schema-2 validators replace the old registry idea. Proposed internal `publishMigrationSet()` performs only the finite file protocol below; it is NOT `Tx.publish`. Invalid/unsupported records return existing `unsupported-record` (exit 4); consent preview uses existing declared `migration-needs-approval` (exit 3), currently unproduced. Stale consent uses `revision-conflict`; ownership failures keep quarantine diagnostics. No new success endpoint is introduced.

Schema 2 includes the companion [configuration design](config-completion.md): work `configEvidence: { hash, serial }`, with stamps on baseline, reservation, review and analyst evidence. Pure conversion initializes each work from freshly validated sources at serial 0; absent/malformed sources refuse conversion. Historical evidence remains unstamped/unbound, never current merely because the work now has a binding. Do not use a contradictory nullable work-binding variant or a whole-configuration payload on every record. Exact stamp fields/bounds/projection and admission consumers remain subject to joint review; do not hash today's settings onto historical evidence.

Upcast both primary and previous independently, and state-shaped archive blobs through the same version-specific rules. Preserve revision, all budget values/reservations, workSeq, generationSeq, session generations, timestamps, grants, consent bindings, source ownership, locks, settings and history. Do not re-pin contracts, accrue time, settle reservations, spend tokens, append a call/accounting record or execute an effect. Existing version reconciliation remains a separate action. Migration consent authorizes format conversion only, not commands, new grants, adoption or proof freshness.

### 16.3 Admission Before Every Writer

Ship and test a schema-1 bridge minimum BEFORE allowing upgrade; name its exact release/build digest in the preview and manifest. It retains schema-1 operation but recognizes the transition fence and refuses schema-2/newer records without fallback. Rollback targets this bridge, not arbitrary historical development binaries. Existing binaries are NOT claimed safe: a schema number/nonce cannot constrain same-user programs that ignore admission.

`compatibility()` first inspects bounded no-follow raw marker, primary, previous and transition metadata, without mkdir, chmod, lock files, ignore files or maintenance. Unsupported primary/newer marker wins over an older valid previous; `safeState` error rendering follows the same rule. For schema > 2 return metadata-only diagnostics (observed schema and writer version if recorded, otherwise unknown), never a schema-1 fallback presented as current. Malformed/unknown schema is not ordinary corruption fallback.

The gate covers `preLock`/`repairLock`, `acquire`/claim/stale-break, `ensureMarker`, tail repair, publish/append, blobs, artifacts/temp creation, eviction/reduction/run caps, sweep, purge and `cleanTemp(remove=true)`. Recheck under the existing exclusive lock before mutation; waiting writers re-admit after acquiring. Direct writer APIs require the admitted operation context, not an unguarded method call. Machine cleanup checks each candidate's ownership/compatibility or leaves it untouched; a temporary-folder name alone is not admission.

Read-only `exists/read/readLog/readBlob/residue`, compatibility and previews perform NO maintenance, tail truncation, quarantine, lock repair or migration recovery. Read schema 1 via an in-memory upcast only when all snapshot inputs match; unstable snapshots refuse/retry. Interrupted migration returns transition diagnostics until an explicit migration/recovery call; never combines partial live files into a view. Diagnostic reads cannot dispatch jobs or create artifacts.

Missing marker in a nonempty directory or dev/ino mismatch means imported, not migratable: read-only reports it unchanged. Only the existing explicit fresh-open quarantine path may act, after compatibility classification, under its bootstrap lock and durable quarantine journal. Move imported migration descriptors/backups as inert entries too; never resume their transitions or restore their authority. Invalid/copied transition metadata cannot synthesize ownership. A valid locally owned unfinished transition takes precedence over ordinary quarantine; unprovable ownership/mismatch refuses without moving anything. Empty new stores retain fresh-init behavior.

### 16.4 Preview, Consent and Owned Consistent Set

Preview reads a bounded stable snapshot, then returns its canonical `factsHash`, schema pair, workspace/tag/marker nonce/dev/ino, bridge/target build identities, source revisions, upcast summary, legacy-unbound evidence counts, backup location/bytes and rollback limits. Hash every source byte, file-presence sentinel, reference inventory and relevant compatibility/configuration design version. Re-read the inventory after capture; under-lock acceptance rechecks all facts. The preview itself creates no question/state/backup file. Answer `yes` plus the exact factsHash is mandatory; decline writes nothing and permits only diagnostics/read-only use under the new binary. CLI quote capture is reported, not proof of human identity.

Refuse upgrade/rollback while any work has `session.inCall`, a pending execution envelope, a live/focused reviewer or analyst reservation, unresolved intent/result work, uncertain accounting, active quarantine/reduction transition or unclassified execution reference. Stop/reconcile those under the supported source kernel first; migration must not cancel/settle them. Ordinary non-execution pending questions are preserved, not answered by migration. Refuse absent/invalid primary or incompatible previous: repair/reconfirm separately, then preview again. Do not turn previous-state recovery into an implicit upgrade.

Proposed set `.tenet/migration-1-2-<id>/` contains independent private byte copies (NOT hard links) of `state`, `state.prev` or explicit absence, `marker`, `log` or absence, `summaries.json` or absence, plus every reachable owned blob/archive record and owned execution/manifest/artifact reference or explicit absence. Resolve references from BOTH states and journal payloads, recursively with bounded cycle detection; verify content hashes, type, schema and path ownership. Unknown reference forms, missing required objects, symlinks, collisions or non-owned destinations refuse; never infer completeness from filenames. Do not copy or restore Git repositories, source files or the transaction lock; their external-effect references must be settled and recorded as non-restorable facts.

Manifest records logical reference -> owned path/hash/size/presence, source and target bytes/digests, revisions, counter/sequence projections, journal/accounting horizon, reduction summary's `from`, backup inventory digest and resource bounds. Schema-2 archive conversions get new hash-named objects and rewritten references; originals stay byte-exact in the backup, no in-place blob rewrite. Converted primary/previous retain their own revisions. Accounted-log bytes and summaries remain byte-exact: add NO migration journal kind. Proposed `migration-transition.json` is separate durable strict metadata, not evidence/authority, and records protocol version 1, direction, id, owner identity, consent facts/quote capture, finite phase, complete manifests and terminal response.

### 16.5 Exact Publication and Recovery

Every durable metadata/file replacement uses private exclusive staging, file fsync, rename and parent-directory fsync; nested backup directories are synced bottom-up. Preserve absent files as absence. Reserve storage for source copies, target files and metadata BEFORE fencing; never evict to make migration fit. Acceptance holds the normal exclusive lock, re-admits/rechecks consent, and waits out all bridge writers. The durable descriptor is the old-writer fence BEFORE any marker/state/previous/journal content changes. Bridge and target binaries recheck it after lock acquisition.

| Phase / durable operation | Live marker / primary / previous / log | Allowed recovery |
|---|---|---|
| No descriptor | 1 / 1 / 1-or-absent / original | No migration; new preview/consent required. |
| `fenced`: descriptor with complete expected source/target hashes | Original set | Complete backup from exact source; changed inputs refuse. |
| `backed-up`: all source copies verified and synced, inventory sealed | Original set | Stage/verify targets; never convert without intact backup. |
| `prepared`: target primary/previous/reference objects synced, terminal response fixed | Original set | Install only the recorded target objects. |
| Install target previous; then target primary; then marker 2, syncing each | 1/1/2, then 1/2/2, then 2/2/2; absent previous remains absent | Descriptor authorizes only these ordered prefixes. |
| `applied`: descriptor terminal metadata synced | Target set; log/summaries original | Return stored migration acknowledgment; no ordinary call replay. |

Marker target preserves workspace/tag/nonce/dev/ino and changes schema only. Descriptor records writer build identity; do not silently extend old marker parsing. Phase is a lower bound: crash after rename but before phase update is resolved by exact recorded before/after hashes and the permitted prefix, never by schema numbers alone. Marker 2 + primary 1, primary 2 + previous 1, changed log, or any unlisted combination refuses. In particular, superseded section 13.4's unconditional marker roll-forward is forbidden. A malformed schema-2 primary NEVER authorizes reading schema-1 previous. Ordinary same-schema corrupt-primary fallback remains only outside migration, with existing authority suspension/accounting rules and version-specific parsing.

Only an explicit retry of the same migration id/facts may complete a fenced transition. Under the lock, verify owner identity, descriptor, backup, target inventory and hashes, then repeat missing steps idempotently. Unknown descriptor version, duplicate ids, missing copies, stale ownership, target collision, changed references or impossible phase stops without guessing, quarantine or overwriting foreign bytes. Abandoned staging may be removed only when named/hash-bound by the descriptor; unrecognized leftovers are diagnostic blockers. Real SIGKILL recovery is required, not a simulation of file contents.

Prepared metadata fixes the migration result payload and acknowledgment response. `applied` persists completion before returning; response loss cannot repeat conversion, accounting or consent. Store completion outside work-session retry caches. While a privacy-safe complete historical response remains available, return it as historical data alongside a freshly rendered current-state envelope. Once backup/privacy deletion removes that payload, use only R2's minimal completion record, not a fabricated exact response. Insufficient verification refuses an old retry; completion metadata never grants authority or claims current readiness. Pending transitions return exit 3 diagnostics, not success.

### 16.6 Rollback Without Losing Later Actions

Proposed conservative eligibility: target files/references/log/summary match the applied manifest exactly, all counters/sequences equal the saved projection, source backup is intact, supported bridge is available, and NO post-upgrade mutating action or pending job/reservation exists. Revision equality alone is insufficient. Before ANY ordinary writer (including tail repair, chmod, cleanup, forget, blob/artifact writes or effect intent), durably set descriptor `rollbackEligible=false`; a crash may conservatively forfeit eligibility but cannot conceal an action. Diagnostic reads and exact migration-ack retries do not forfeit it. This guard must cover launch/finalize transactions too.

`previewRollback()` reports eligibility and reasons without writes. Only new fact-bound explicit `rollback-migration` consent can restore. Use the same descriptor with `direction=rollback`, a new consent and fixed response; old writers remain fenced. Verify the full target set, stage saved primary/previous, then restore previous, primary, original marker LAST; log/summaries are verified unchanged and retained byte-exact. Restore original reference inventory without deleting unrelated files or restoring source/Git; do not lower any counters or generations. Record `rolled-back` and the exact acknowledgment durably before releasing bridge access. Recognize only recorded before/after prefixes on killed rollback, as on upgrade. Keep terminal metadata so old upgrade consent cannot reapply; a new upgrade needs a new preview/id.

If any post-upgrade mutation occurred, refuse restore; do not copy an old budget over a higher one or discard new decisions/lessons/jobs. No merge/downcast/manual-restore support is claimed. An arbitrary older binary may damage files outside this protocol and is explicitly unsupported. The bridge's handling of rolled-back metadata is part of its qualification, not something today's schema-1 kernel already does.

### 16.7 Unknown Fields, Retention and Forgetting

Proposed per-record rule: only informational unknown keys explicitly allow-listed by the reviewed schema-1 parser may move losslessly to root `_ext.safe_ext[recordPointer][key]`; all other unknown keys refuse. No heuristic classification by spelling, and no unknown-key stripping. The allow-list must enumerate concrete keys before implementation; currently none is approved. Pointer escaping is canonical, array entries use stable ids where available, and duplicate ids, pointer/key collisions, an existing conflicting `safe_ext` or an unknown required record type refuse. Safe extensions are inert, never read by authority/evidence consumers, and round-trip through future publications and rollback.

| Record family (including nested members) | Unknown-field handling |
|---|---|
| State/project/intent overview, decision prose, plan prose, lessons and archive descriptive metadata | Reviewed informational keys only -> per-record `safe_ext`; unknown semantic/reference keys refuse. |
| Work/session/pins, basis/verifiedBy, obligations/baselines, receipts/provenance/envelopes, review/coverage/finding/disposition, analyst/model, reservations/budget/accounting, locks/anchors, git/dependency state | Strict: these influence proof, spending, identity or protection; unknown keys refuse, never become safe extensions. |
| Grants/bindings/scope, config/settings/restrictions, policy/trust/adoption, consents/questions, ownership/quarantine, marker/transition/backup manifests, journal intent/result operation payloads | Strict recursively; no permissive `_ext` can hide authority, executable or recovery fields. |

Existing [schemas.ts](../packages/kernel/src/core/schemas.ts) has strict root/authority objects but many nested `z.object`s that strip fields, and journal outer records pass unknown keys. Implement version-aware classification BEFORE those parsers and enforce it in every publisher/reader, including accounting entries, archives and previous state. Unknown complete journal records refuse; a torn tail is preserved byte-exact in the backup and diagnosed. Proposal refuses migration until tail repair has been separately authorized/completed by the bridge and preview refreshed.

R1 approved (owner, 2026-10-24, conversation decision 13 option A): retain the source recovery set protected while rollback is eligible, then keep it until explicit previewed deletion. Do not auto-evict it or its pinned references. Total bytes count toward storage ceilings; pressure refuses data-adding work rather than silently removing protected copies. Confirmed forgetting overrides retention and must purge controlled copies even when this makes rollback unavailable. Keeping the backup never makes an otherwise unsafe rollback permissible. No automatic expiry duration is introduced. The concrete deletion/crash-recovery interface still requires review and final sign-off. `reduceLog`, `prevRevision`, summaries and temp caps must protect migration references/accounting horizons; no reduction during transition, and later reduction first forfeits rollback. Existing cleanup gains no implicit backup-deletion authority.

Confirmed `forget` must invalidate rollback BEFORE touching lesson-bearing data, durably record an opaque privacy intent (id/references, no lesson text), then delete the entire migration recovery set and its lesson-bearing staging/target copies rather than silently altering a byte-exact backup. Traverse owned archive/blob/packet copies and primary/previous too; preserve current counters and history not containing the lesson. Remove only proven owned copies; inability to classify or purge a controlled copy blocks success and restoration. Finish both state publications and purge before acknowledging; a kill resumes the privacy intent before any migration/rollback/ordinary writer can expose a forgotten copy. Tombstoned/deleting sets are never restorable even if their bytes survive a crash. Report outside/uncontrolled copies honestly, not secure-erasure guarantees. This expands existing forgetting and needs CON-10 tests; exact privacy-intent representation is a review blocker, not an implemented guarantee.

### 18.2 Rollback Ordered Prefixes

Let T = exact applied target bytes, S = saved source bytes, A = source-prev absence sentinel. Entry requires section 16.6's no-later-mutation predicate and intact independent source copies, no hard links. Create a new rollback operation id linked in active metadata to the completed upgrade; never overwrite its completion identity. Fence both bridge/target writers before staging. Each replacement/unlink and descriptor update uses section 16.5 fsync ordering; phase is a lower bound verified against hashes.

| Durable prefix (previous / primary / marker) | Only next recovery operation |
|---|---|
| T / T / T; rollback fence + staged S durable | Restore previous to S, or unlink target previous if source sentinel is A; sync parent. |
| S-or-A / T / T | Restore source primary; sync parent. |
| S-or-A / S / T | Restore source marker LAST; sync parent. |
| S-or-A / S / S | Persist rolled-back completion, then release rollback fence; bridge may operate only after terminal verification. |

If source previous was absent, the first operation is verified absence/unlink, not creation of a synthetic previous; if target previous was also absent it is an idempotent no-op. At every prefix verify unchanged log/summaries and full source/target inventories; converted immutable target blobs can remain pinned inert copies until explicit deletion, but restored State references only source blobs. No Git/source restore or unrelated-file deletion. Equal before/after bytes collapse prefixes only when every possible next step is equivalent; otherwise refuse. Any other tuple, changed object, missing required saved copy or higher counter/validity/launch high-water refuses. Rollback never lowers the companion's fences; inability to restore without losing its high-water blocks rollback, not a license to erase it.

Pristine rollback (owner-approved amendment 2026-10-27, [migration-closure.md §3.2](migration-closure.md#32-mc-4-rollback-needs-no-floor-carrier)): entry also checks, from the live target bytes and not only from `rollbackEligible`, that `jobSeq` is 0, the job table is empty, every validity serial is 0, no work or evidence stamp has a serial above 0, and the journal after the applied phase holds no `launch` record or version-2 effect payload. Section 16.6's exact-manifest match implies this; the check is a second guard. Between S/S/S and persisting rolled-back completion, delete each manifest-listed upgrade-created object after verifying its recorded hash; absence counts as deleted, a mismatch stops without completing, and recovery repeats this step from the descriptor. This replaces the sentence above that lets converted target blobs remain until explicit deletion. No floor carrier is needed: the rolled-back lineage issued no identity above the initial floor, so a later re-upgrade (new preview, consent and id) starts at the initial floor without reusing any issued identity.

### 18.3 Minimal Terminal Record and Retry

Proposed terminal JSON has EXACTLY five required keys: `{operationId,protocolVersion,versions,outcome,bindingDigest}`. operationId = opaque random 128-bit lowercase hex; protocolVersion = 1; versions = strict `{from,to}` safe positive format integers (1/2 or 2/1); outcome = `upgraded` or `rolled-back`; bindingDigest = full lowercase SHA-256 of the canonical approved operation facts, not an individual lesson hash. No additional keys/nested extensions; no timestamps, build/path/owner/lesson ids, quotes, response envelope, output or payload. Operation type is already implied by versions/outcome; deletion does not rewrite a successful upgrade into a new outcome. Active descriptor, deletion intent and ownership evidence are separate nonterminal records removed/minimized as below.

After backup deletion recognize only exact `(operationId,protocolVersion,versions,bindingDigest)` against one strict local terminal record in an independently admitted owned store. Return only that historical terminal fact with a freshly admitted current envelope, never the old response, readiness or proof. Unknown id, digest/version mismatch, malformed/extra field, duplicate identity, copied/unowned store or insufficient current admission refuses historical replay without conversion/spend. An old consent cannot start another operation; a new upgrade requires new facts/id/consent. A bridge must understand the terminal version pair before allowing rolled-back schema-1 writes. Removing local records removes this recognition; absence is not evidence of nonexecution and never permits replay of an old id.

### 18.4 Explicit Deletion and Forget Recovery

Owner-approved amendment 2026-10-27: for forgetting, this section is superseded by [migration-closure.md §3.1](migration-closure.md#31-mc-3-crash-safe-forgetting-through-the-effect-journal). Forget is a `forget` journal effect (intent, purge of `manifests/` packets and owned recovery sets while the text is admitted, two ordinary publications, result) with a recovery reconciler. The privacy intent file, tombstone, staged sanitized replacements and fixed P1/P2 publication prefixes below no longer apply to forgetting, because no lesson text exists in logs or blobs to sanitize. `.tenet/migration-privacy.json` stays reserved and refused by the stage-19 bridge; nothing writes it. The text below remains the proposal for explicit `backup-delete` only, pending its own review.

Proposed internal `backup-delete` and `forget-copy-purge` operation labels are not decision registry additions. Explicit backup deletion previews the sealed recovery-set inventory/bytes, forfeited rollback and R2 remainder; acceptance binds current facts and a new opaque operationId. Forget confirmation has priority over R1 and deletes the entire lesson-bearing recovery set, not a modified backup. No automatic expiry/cleanup authority is added. Both use the same exclusive lock/admission gate; only their recovery can run while their intent is pending, including when rollback left schema 1 live.

Intent is strict active metadata `{protocolVersion,operationId,kind,owner,phase,targets,replacements,completionIds}`: kind backup-delete/forget-copy-purge; owner exact marker identity; phase prepared/tombstoned/replaced/purged; targets finite entries `{root,relative,dev,ino,hash,bytes}`; replacements `{target,staged,hash,bytes}`; completionIds opaque migration ids. Roots are enumerated owned store/workspace-temp roots, never arbitrary absolute inputs; relative paths reject traversal/links, retain capture identity and revalidate no-follow immediately before action. `target`/`staged` use the same typed locator; entries are immutable after acceptance. No plaintext lesson, quote, text search needle, command output or user-supplied free text is stored in this intent. Duplicate/overlapping locators refuse. An absent target after a recorded deletion is idempotent; an identity/hash mismatch is not permission to delete the replacement.

For forget, while the lesson is still available in admitted source memory, enumerate all controlled copies before changing anything; select text-bearing packets/blobs/log/cache copies using statement/quote and structured lesson id, then stage already-sanitized replacement bytes. Clear cached responses as existing withoutLesson does; remove the lesson record, preserve unrelated active work, grants, locks, counters, other lessons and history. Do not cancel unrelated sessions or discard a whole shared State/log to erase one lesson. Referenced structured blobs get sanitized replacements and rewritten references; no in-place hash-object edits. Any active affected reader/job must first be quiesced under the source kernel; unrelated active records survive unchanged. Unknown archive/cache/free-text encodings or a copy that cannot be sanitized without altering unrelated binding facts block successful forgetting; identify that limitation, never claim a complete purge.

| Durable ordering | Recovery and exposure rule |
|---|---|
| Stage sanitized replacements + complete inventory; fsync, then persist prepared intent | No destructive action yet. Before intent, orphan staging is sanitized/non-authoritative, never a restore source; after intent, fence reads/caches/writers that could expose old copies. |
| Persist set tombstone and rollbackEligible=false; sync BEFORE any purge/update | Upgrade/rollback/retry must consult privacy intent/tombstone before backup/terminal access. A crash cannot make surviving backup bytes restorable. |
| Publish sanitized current State; publish again so previous is sanitized; install sanitized log/blob references using recorded prefixes | Use recorded sanitized inputs, not text remembered across restart. Maintain revisions/accounting and the companion's validity/launch fences; no proof restamping. If an intermediate publication leaves unsanitized previous, the intent still blocks exposure/fallback. |
| Delete sealed backup/staging/captured affected artifacts and superseded lesson-bearing blobs; sync each affected parent | Backup-delete skips State/log rewrites and never deletes live shared blobs merely because backup pins them. Forget deletes a blob only after every surviving reference has been replaced; unrelated bytes/records are preserved. |
| Verify absence/replacements; persist purged phase; keep/validate minimal terminal; erase payload-bearing transition metadata; sync; remove intent LAST | Terminal/tombstone protection remains until no backup or payload-bearing descriptor survives. Crash before intent removal repeats recorded verification; crash afterward cannot restore deleted data. A missing/changed required replacement blocks completion. |

The deletion plan names all payload-bearing descriptor/response files as targets too; stripping a quote only from the backup is insufficient. Keep the owned stable paths and completed-target cursor only while deletion is pending, then remove them. A deletion retry recognizes its same pending id; after intent removal use a fresh read-only absence preview, not a retained deletion response or invented R2 outcome. Tombstone may be removed only after every named restorable set/staging copy is absent and surviving descriptor is reduced to strict terminal form. Privacy failure stays fenced and reported; no secure-erasure or host-memory guarantee.

Exact privacy publication prefixes: with original primary P at revision r and previous V (possibly absent), stage sanitized P1 at r+1 and P2 at r+2 plus their exact accounting/log images. Admit only `(previous,primary) = (V,P) -> (P,P) -> (P,P1) -> (P1,P1) -> (P1,P2)` with recorded file hashes/presence and separately recorded append/install prefixes; repeated identical values collapse only equivalent steps. The two rotation prefixes retain the privacy fence even though old P may still contain text. Stage immutable replacement inputs before the intent, including the companion's unchanged/increased high-water records; resume missing bytes/steps, never call ordinary Tx.publish again to allocate another revision. Every accounting append is identity/hash-bound and settles once. Intent phase remains a lower bound; an unlisted log/state combination refuses. Targets enumerate regular-file leaves; remove inventoried directories bottom-up only after verified empty, without recursive deletion of newly appeared entries. No plaintext lesson is needed on restart because every replacement and deletion target is already fixed.

### 18.5 Storage, Pins and Compaction

Pins are the union of both states' concrete edges, sealed recovery inventories, pending transitions/privacy replacements and the companion's recovery/launch horizons.
