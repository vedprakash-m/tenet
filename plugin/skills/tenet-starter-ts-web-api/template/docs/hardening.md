# Hardening notes

What this project is **not**, yet. Every shortcut and every prototype adds to this list; nothing here is a surprise.

- **Development identities only.** The first run seeds `admin@example.test` and `member@example.test` with random passwords saved in `.env.local` (git-ignored). They exist for local use on your own machine. Do not run this on a shared machine.
- **Browser scope.** The React/Vite shell covers account access only. Domain journeys, a reference workload, API compatibility enforcement and per-changed-journey obligations remain unfinished. `docs/asvs.md` publishes all pinned Level 1 IDs with initial applicability/method/results; full requirement verification, known gaps and independent approval remain open, not ASVS conformance. Axe/keyboard automation is not full WCAG conformance; manual screen-reader results must be recorded in `docs/a11y-checks.md`.
- **Local binding only.** The API and Vite listen on `127.0.0.1`; Vite uses port 5173 and proxies the API. Any other binding, and any TLS termination, is a consequential change to decide and record here first.
- **No TLS.** Cookies are not marked `Secure` outside production.
- **One node.** SQLite in WAL mode is a single-node envelope. Writes that protect an invariant use immediate transactions; a busy database is retried for a second and then answers 503.
- **No email.** There is no password reset by email and no verification.
- **Backups are manual.** `platform/backup.ts` makes and verifies a copy and migrations take one before changing a database that has data; there is no schedule. `npm run restore -- <backup>` puts a verified copy back (stop the app first); the replaced database is kept beside it, and a copy written by newer code is refused. The app and the restore tool each take `<db>.owner`, so restore refuses while an app is running even if it holds no lock. If a restore is interrupted, a `.restore-in-progress` marker stays, the app will not start, and `npm run restore -- --finish` or `--rollback` settles it. Restore never touches anything but the database file: uploads and other external state are not covered.
- **Production secrets.** `COOKIE_SECRET` (32+ characters) is required in production and is never committed.
- **Logging scope.** Structured root and one-level authentication fields, request cookies/authorization/CSRF headers and response cookies have explicit redaction paths. This is not arbitrary-content sanitization: do not log bodies, URLs with credentials, secrets in messages or internal errors containing user input. Unexpected error stacks stay in local logs, not responses; restrict log access and define retention before shared use.
- **Deployment checklist.** Not written: this project does not deploy anything.

- **Minimum runtime.** The graph is pinned for Node 22.12.0 and CI installs with engine-strict on that runtime. TypeScript-ESLint 8.55.0 is retained because 8.56+ selects visitor keys requiring Node 22.13; do not raise the runtime floor or force a visitor-key major override during a dependency refresh. Check compatibility and advisories together.

- **Browser prerequisite.** Local browser checks require the Chromium build matched to Playwright. It is a separate host-cache download, not part of the pinned npm install. The README names the command; obtain permission before a helper runs that installation. The validated environment had the matching browser already cached. Clean-host bootstrap and browser-binary identity still need their own evidence.

- **API contract scope.** `npm run --silent openapi` exports the registered runtime schemas and cookie/CSRF declarations. It uses only an ephemeral database, does not listen, and ignores ambient configuration. No endpoint or Swagger UI serves this document. Metadata is not authorization; enforce actor/object/role checks in the feature and test denials. There is no automatic breaking-change comparison, trait-based finding or semver gate yet. Invalid response data now fails serialization against the shared schema rather than widening the published shape.

- **Lint dependency maintenance.** A clean install reports upstream deprecation for the retained ESLint 9.39.1 pin. The Node 22.12 engine-strict install still passes and the checked registry audit reports zero advisories; neither is a maintenance-support or security guarantee. Reassess the lint stack before qualification while preserving the declared runtime floor.

- **Restore compatibility.** A backup must have a known forward-only migration history with matching checksums and valid foreign keys. A familiar filename/version alone is insufficient. Copies from edited or divergent migration histories require the code that wrote them or an explicit data migration; restore will not reset or relabel their history. An interrupted refusal keeps the recovery marker and originals aside. New markers record whether a database originally existed: rollback to absence keeps installed or changed database/log files at the reported `before-restore` path rather than deleting them. Inspect retained files before manually removing them. A collision, unreadable marker, or older marker without enough information to establish the original state refuses rollback and keeps the marker; preserve the files for manual recovery. A readable older marker can still finish using its verified backup. Stop every database user before recovery; stale-owner concurrency remains unqualified.
- **Unrecorded data before migration.** An existing user-table schema also requires a verified backup before the first migration, even with no recorded history; an occupied backup destination refuses before migration SQL or its history entry. Empty user tables are conservatively protected too. Only the literal `sqlite_` prefix is internal; names such as `sqliteNotes` remain user tables for backup and restore checks. The backup retains empty history rather than inventing compatibility, so the strict restore command still refuses an unrecorded user schema. Use the originating code or an explicit data migration. Ledger initialization and SQLite checkpoint housekeeping can occur before refusal; no byte-identical whole-database or concurrent-writer guarantee follows.
- **Restore marker validation.** A marker must be an object with nonempty backup/aside paths, a finite nonnegative timestamp and, when present, a boolean original-presence field. Valid JSON alone is insufficient: `null`, scalar values and malformed records keep startup and new restores fenced. Recovery refuses before changing ownership and does not erase the invalid marker.
- **Database owner admission.** An existing owner record must contain exactly a positive safe-integer process ID and a string start time. Malformed or unreadable records are preserved and startup/restore refuses; preserve the data and verify ownership manually before recovery. A signal error establishes PID absence only for `ESRCH`; other unexpected signal errors propagate without removing the record. A live PID with unavailable recorded/current start time stays in use. These checks do not repair concurrent stale-owner replacement or release races.

- **Restore checkpoint admission.** A new restore requires SQLite's WAL truncate checkpoint to report not busy; a nonthrowing busy result refuses before the restore marker or file moves. A reader holding WAL frames remains readable, and the backup/log are preserved; restore can retry after database users close. This is a point-in-time check, not exclusion of external connections that open later or qualification of interrupted recovery races.
- **Restore backup aliases.** Backups must be separate files. Resolved names and device/file identities reject symbolic and hard links to the live database or its sidecars before backup reads, markers or moves. This preflight does not make path inspection atomic against concurrent replacement.
- **Restore retained destinations.** A new restore refuses any occupied generated kept-aside database or sidecar path before its marker or moves. Earlier retained content is never treated as belonging to this new restore. This is a point-in-time preflight, not reservation against external creation; interrupted recovery still uses its existing marker-based rules.
- **Restore staging entries.** A new restore refuses existing install-copy/sidecar staging entries and the marker temporary entry before writing its marker or moving files. Preserve unknown staging content for manual inspection; a new operation cannot claim it as its own. This is a point-in-time check, not external path reservation or a change to interrupted recovery.
- **Unreadable restore-marker entries.** A dangling marker link or failed marker-entry inspection cannot establish absence. Startup/new restore remain fenced, and recovery reports unreadable marker data before ownership writes. Preserve the entry and database for manual inspection; this does not establish atomic path inspection against replacement.

- **Admission envelope.** Each live API process allows 6,000 attempts/minute per normalized network IP before lookup/body/hash work, 120/minute for anonymous/credential traffic, and 300/minute per verified user for operations and session management. Sign-in retains five/minute per IP/account; password attempts additionally allow five/minute per verified user. Session rotation/IP changes do not reset user budgets. Fixed-window counters are volatile and retain at most 5,000 keys each; restart/eviction and shared-network exhaustion limit the guarantee. This loopback single-process envelope is not public multi-node qualification.
- **Status and authority.** Only GET `/api/auth/me` without any `sid` cookie uses the coarse ceiling alone for its constant signed-out 401, with no lookup/write/hash. Empty/forged/expired/revoked cookies get no such path. Admission identity never authorizes: the session/user is read again inside bounded maintenance before handlers. Refused admission changes no session rows/cookies. Coarse/user exhaustion can still deny service until reset. Quota/retry/correlation headers identify the applicable layer.
- **Route metadata.** Grouped rate-limit metadata is unsupported. Startup checks collected options only; later/detached metadata may evade that diagnostic. Actual-request normalization accepts own-data plain/null-prototype options, pins an own undefined group and seals just the rate-limit binding before counters. Unsafe metadata gets a generic 500; no partitioned counter or universal pre-listen guarantee. Per-route opt-out cannot disable mandatory admission. New admission/session files are protected recipe paths. Existing generated projects are not automatically updated.
- **Validation scope.** Browser assertions use a fresh source-built production UI with real admission. The exhaustion case owns another source server/database/token so it does not consume the unrelated journeys' quota; it does not reset/exempt the API. Memory, full reference traffic/fitness consumers, API compatibility and broader security/accessibility qualification remain open until measured and reviewed.
