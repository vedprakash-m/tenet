# Guarded Git filter preparation

2026-10-20 · base `d457714` · local, uncommitted · follow-up to reassessment R04

The cloud filter-consent implementation allowed `expectedTree` to execute filters while the transaction was held, before commit intent or process ownership was published. The adapter rebuilt the filtered tree again before its guarded commit process. Consent did not provide process admission, cancellation, timeout or environment controls.

The intent tree now disables filters and filesystem monitors. The existing commit intent, prepared sentinel and `inCall` are published before configured staging. Staging and commit use the existing runner and its admission transaction, private index, minimal environment, recorded process group and bounded timeout. Consent is revalidated against current commands before staging; enabled command values are pinned. Assignment order enters the hash because Git's last duplicate assignment wins. No scheduler, state format, host dependency or budget increase was introduced.

Staging failures do not launch a commit. Working-file changes made by a filter remain present and prevent committing the old checked candidate. A transformed tree refuses with `capability-missing` until committed-tree checks exist. If HEAD moves during preparation, the outcome is uncertain. Recovery checks the known contract's exact `Tenet-Work` trailer in addition to the parent/tree/path postcondition; a failed tree inspection is not an empty diff.

`stop` during preparation stops the identified group but returns the existing unresolved-effect fence. It retains source ownership until a subsequent policy-aware call verifies HEAD. SIGKILL recovery follows the same rule; it does not automatically replay the filter or commit. This preserves the separation between process cancellation and effect reconciliation.

`filter-jobs.test.ts` adds sixteen controls using actual Git and programs: neutral consented-filter preparation; neutral filesystem monitors; one admitted staging/commit sequence and a stripped synthetic environment canary; required-filter failure with human staging preservation; transformed content; working-file mutation preservation; durable intent/ownership before launch; stop before launch; TERM-resistant filter and child timeout; stop during staging; kernel SIGKILL and recovery; changed cached commands; reordered duplicate commands; successful and failing HEAD-moving filters; unreadable intent-tree reconciliation. Existing Git, hook, commit crash and index recovery controls remain in the full suite.

The first seven regressions failed on the original path. Separate red controls caught filesystem-monitor execution, order-insensitive consent and unreadable-tree recovery. A corrected HEAD-moving fixture also exposed the failed-preparation outcome path. During fixture development, embedded script escaping and the nested Git index were corrected; invalid fixture failures are not counted as product counterexamples. An initially overstrict invocation count was replaced by the specified job-dispatch assertion: Git can invoke a clean filter repeatedly inside one admitted command. No product assertion was relaxed to permit unguarded execution. Stop expectations explicitly assert the existing unresolved-effect fence and retained ownership.

Five built-CLI scenarios exercise pass-through execution with a canary, transformation refusal, working-file mutation, stop and SIGKILL recovery, including real human staging. Reviewer pass data remains synthetic protocol input. Host behavior is unobserved and host runs remain deferred.
