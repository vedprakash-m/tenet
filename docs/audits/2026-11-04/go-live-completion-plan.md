## 1. Decision and recommendation

**A qualified public R1 release today is not supported by the current evidence.**
The fastest responsible target today is an accepted stabilization candidate and
an explicit go/no-go decision. If the owner selects a private evaluation instead,
it must be operator-controlled, use disposable copies and synthetic data, and
carry no R1, production-safety or native-qualification claim. It is not a
substitute for the public review window or a workaround for release safeguards.
That alternative has not been selected or approved.

If "live" means production use on valuable repositories or data, the current
recommendation is **no-go**: dependency recovery can overwrite unknown human
content. A warning or renamed release does not repair it.

The full R1 completion path below retains every Must and every applicable gate
in plan sections 4-9 and 12.19-12.21. Existing cuts remain exactly those in
plan section 11.2. In particular, sealed-baseline classification is still due,
prototype promotion is not cuttable, and a recipe-upgrade cut does not waive
contract recipe identity.

## 6. Staffing and execution controls

- **One integration/safety owner** owns pipeline, schema, store, ports, counters,
  configuration identity and recovery changes. Reviewers are independent, not
  simultaneous competing writers in these files.
- **One starter/adapter owner** handles independently owned platform/tests and
  real runtime characterization. Share stable APIs before editing common owners.
- **One QA/qualification owner**, with UX/evaluation and release-owner decisions,
  runs exact-artifact acceptance, evidence review and external coordination.
  Agent output cannot replace a required human or second-maintainer role.

These are recommended responsibilities, not newly assigned people or launched
sessions. Two disjoint implementation streams plus one integration/validation
stream are preferable to many agents repeatedly touching the central protocol.
External participant access is a separate constraint, not solved by staffing
more coding agents.

At each integrated capability: failing distinguishing tests -> minimal repair ->
focused real-boundary acceptance -> independent disposition -> affected fast
gates. At each coherent candidate: full supported `npm run ci`, built
dual-runtime UAT, exact evidence, then freeze. Run independent OS jobs in
parallel, but do not compete heavyweight full suites on the same host.
Any later runtime/payload change creates a new artifact; retain earlier evidence
as history and rerun the gates affected by the change before acceptance.
The final release artifact needs its own complete gates.

Use the plan and acceptance worklist, not accumulating chat logs, as the handoff.
For each package report: implemented, focused-accepted, supported-accepted,
host-observed and formally-qualified separately, plus exact open obligation,
owner and next dependency. Do not sum overlapping tests or call these columns
interchangeable percentages.
